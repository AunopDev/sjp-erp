# ออกแบบ API

ใช้เมื่อเพิ่มหรือเปลี่ยน endpoint, event, หรือ contract ระหว่างระบบ ถ้าโปรเจ็กต์มีรูปแบบ API อยู่แล้ว ให้ทำตามรูปแบบเดิมก่อน ไฟล์นี้ใช้กับส่วนที่โปรเจ็กต์ยังไม่ได้กำหนด ตัวอย่างโค้ดอยู่ใน [code-examples.md](code-examples.md) และตัวอย่าง contract ครบชุดอยู่ใน [worked-example.md](worked-example.md) หัวข้อ 6

## ขั้นตอน

1. ระบุผู้เรียกและสิ่งที่ผู้เรียกต้องการทำ เป็นประโยค "ผู้เรียกต้องการ ..." หนึ่งประโยคต่อ endpoint
2. เปิด endpoint ที่มีอยู่ 2–3 ตัวในโปรเจ็กต์ จดรูปแบบ: path, ชื่อฟิลด์, รูปร่าง error, pagination, การยืนยันตัวตน
3. กรอกตาราง contract ด้านล่างให้ครบทุกช่อง
4. เขียน schema ของ params, query, body และ response
5. ตรวจตามรายการท้ายไฟล์
6. ปรับ OpenAPI หรือเอกสาร API ที่โปรเจ็กต์ใช้ ให้ตรงกับ schema

## ตาราง contract

กรอกหนึ่งตารางต่อ endpoint ช่องที่กรอกไม่ได้คือคำถามที่ต้องหาคำตอบก่อนเขียนโค้ด

| หัวข้อ | สิ่งที่ต้องระบุ |
| --- | --- |
| Method และ path | เช่น `POST /orders` |
| จุดประสงค์ | หนึ่งประโยค |
| ใครเรียกได้ | ต้องเข้าสู่ระบบหรือไม่ role ไหน เป็นเจ้าของข้อมูลหรือไม่ |
| Params / query | ชื่อ ชนิด ข้อจำกัด ค่าเริ่มต้น |
| Body | ฟิลด์ ชนิด บังคับหรือไม่ ข้อจำกัด |
| Response สำเร็จ | status และฟิลด์ที่ส่งกลับ |
| Response ผิดพลาด | ทุกกรณี: status, code, เมื่อไรเกิด |
| ส่งซ้ำ | เรียกซ้ำแล้วเกิดอะไร ใช้กลไกอะไรกันซ้ำ |
| ผลข้างเคียง | เขียนตารางไหน เรียกระบบภายนอกอะไร ส่งแจ้งเตือนอะไร |
| ผู้ใช้เดิม | ใครเรียก endpoint นี้อยู่ การเปลี่ยนกระทบหรือไม่ |

## Path และ method

- Path เป็นคำนามพหูพจน์ของทรัพยากร ตัวพิมพ์เล็ก คั่นด้วยขีด: `/leave-requests`, `/leave-requests/{id}`
- ทรัพยากรย่อยอยู่ใต้ทรัพยากรแม่ไม่เกินสองชั้น: `/orders/{id}/items`
- การกระทำที่ไม่ใช่การอ่าน สร้าง แก้ ลบ ตรง ๆ ใช้ POST กับกริยาต่อท้าย: `POST /leave-requests/{id}/cancel`

| Method | ใช้เมื่อ | เรียกซ้ำ | status สำเร็จ |
| --- | --- | --- | --- |
| GET | อ่าน ไม่เปลี่ยนข้อมูล | ได้ผลเดิม | 200 |
| POST | สร้าง หรือสั่งการกระทำ | ต้องมีกลไกกันซ้ำ | 201 เมื่อสร้าง, 200 เมื่อสั่งการกระทำ |
| PUT | แทนที่ทั้งรายการ | ได้ผลเดิม | 200 |
| PATCH | แก้บางฟิลด์ | ออกแบบให้ได้ผลเดิม | 200 |
| DELETE | ลบ | ได้ผลเดิม (ลบซ้ำไม่ error) | 204 |

GET ห้ามมีผลข้างเคียง เพราะ browser, proxy และตัว retry อาจเรียกซ้ำเองได้

## Status และรูปร่าง error

| status | ความหมาย | ใช้เมื่อ |
| --- | --- | --- |
| 400 | ข้อมูลที่ส่งมาผิดรูปแบบ | validate ไม่ผ่าน |
| 401 | ไม่รู้ว่าเป็นใคร | ไม่มีหรือ token หมดอายุ |
| 403 | รู้ว่าเป็นใคร แต่ไม่มีสิทธิ์ | role ไม่พอสำหรับการกระทำนี้ |
| 404 | ไม่มีทรัพยากร | ไม่พบ หรือเป็นของคนอื่นและไม่ควรรู้ว่ามี |
| 409 | ขัดกับสถานะปัจจุบัน | ซ้ำ, สถานะไม่อนุญาต, ถูกแก้ไปแล้ว |
| 422 | รูปแบบถูกแต่ผิดกฎธุรกิจ | ใช้เมื่อโปรเจ็กต์แยกจาก 400 อยู่แล้ว |
| 429 | เรียกถี่เกิน | มี rate limit |
| 500 | ระบบผิดพลาด | error ที่ไม่ได้คาด |

error ทุกตัวใช้รูปร่างเดียวกันทั้งระบบ:

```json
{
  "code": "VALIDATION_ERROR",
  "message": "ข้อมูลคำสั่งซื้อไม่ถูกต้อง",
  "trace_id": "…",
  "details": [{ "path": ["items", 0, "quantity"], "message": "ต้องมากกว่า 0" }]
}
```

`code` เป็นค่าคงที่ให้โปรแกรมใช้ตัดสินใจ `message` เป็นข้อความให้คนอ่าน ผู้เรียกห้ามตัดสินใจจากข้อความ ไม่ส่ง stack trace, ชื่อตาราง, หรือข้อความจากฐานข้อมูลออกไป

## รายการและ pagination

- ทุก endpoint ที่คืนรายการมี `limit` พร้อมค่าเริ่มต้นและค่าสูงสุด
- รูปร่าง response: `{ "items": [...], "next_cursor": "…" | null }` ไม่คืน array เปล่า ๆ ที่ชั้นบนสุด เพราะเพิ่มฟิลด์ภายหลังไม่ได้
- ข้อมูลที่โตต่อเนื่องใช้ cursor ข้อมูลขนาดเล็กคงที่ใช้ `page` และ `limit` ได้
- ตัวกรองและการเรียงรับเฉพาะค่าที่อยู่ในรายการอนุญาต ห้ามนำชื่อคอลัมน์จากผู้เรียกไปต่อ SQL

## การส่งซ้ำ

| ชนิด | กลไก |
| --- | --- |
| สร้างข้อมูล | ผู้เรียกส่ง header `Idempotency-Key` server เก็บ key ด้วย unique constraint คำขอซ้ำคืนผลเดิม |
| เปลี่ยนสถานะ | `UPDATE ... WHERE สถานะ = สถานะที่คาด` แล้วตรวจจำนวนแถว |
| แก้ข้อมูลที่หลายคนแก้ได้ | ส่ง version หรือค่าคอลัมน์ `<ชื่อ>_update_date` ที่อ่านมา server ปฏิเสธด้วย 409 เมื่อไม่ตรง |
| รับ webhook หรือข้อความจากอุปกรณ์ | เก็บ id ของเหตุการณ์ ตัดรายการที่เคยรับแล้ว |

## การเปลี่ยน API ที่มีผู้ใช้

การเปลี่ยนที่ไม่ทำให้ผู้เรียกเดิมพัง: เพิ่ม endpoint, เพิ่มฟิลด์ที่ไม่บังคับใน request, เพิ่มฟิลด์ใน response

การเปลี่ยนที่ทำให้พัง ต้องหยุดถามเจ้าของก่อน: ลบหรือเปลี่ยนชื่อฟิลด์, เปลี่ยนชนิด, เพิ่มฟิลด์บังคับ, เปลี่ยนความหมายของค่าเดิม, เปลี่ยน status code, เพิ่มค่าใหม่ใน enum ที่ผู้เรียกใช้ switch

เมื่อจำเป็นต้องเปลี่ยนแบบพัง ให้เสนอทางที่ของเก่าและใหม่อยู่ร่วมกันช่วงหนึ่ง: เพิ่มฟิลด์ใหม่คู่กับฟิลด์เก่า หรือเพิ่ม endpoint รุ่นใหม่ แล้วค่อยถอดของเก่าเมื่อผู้เรียกย้ายครบ

## ตรวจก่อนส่ง

- [ ] ชื่อฟิลด์ใช้รูปแบบเดียวกับ API เดิมของโปรเจ็กต์
- [ ] ทุก input มี schema และมีขีดจำกัด (ความยาว, จำนวน, ช่วงค่า)
- [ ] response ผ่าน schema ที่เลือกฟิลด์ ไม่ส่งแถวจากฐานข้อมูลออกไปตรง ๆ
- [ ] ตรวจทั้งตัวตนและความเป็นเจ้าของข้อมูล
- [ ] POST ที่สร้างข้อมูลมีกลไกกันซ้ำ
- [ ] รายการมี limit สูงสุด
- [ ] ไม่ทำให้ผู้เรียกเดิมพัง หรือได้ถามเจ้าของแล้ว
- [ ] เอกสาร API ตรงกับ schema
