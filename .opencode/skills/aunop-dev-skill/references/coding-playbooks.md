# ขั้นตอนทำงานโค้ดแยกตามชนิดงาน

เลือก playbook ที่ตรงกับงาน แล้วทำทีละขั้นตามลำดับ แต่ละขั้นมี "ผลที่ต้องได้" ถ้ายังไม่ได้ผลนั้นอย่าข้ามไปขั้นถัดไป กฎโค้ดอยู่ใน [coding-standards.md](coding-standards.md) ตัวอย่างอยู่ใน [code-examples.md](code-examples.md) และตัวอย่างงานทั้งเส้นอยู่ใน [worked-example.md](worked-example.md)

## สารบัญ

- A. สำรวจโปรเจ็กต์ (ทำก่อนทุก playbook เมื่อยังไม่รู้จักโปรเจ็กต์)
- B. ฟีเจอร์ใหม่
- C. แก้บั๊ก
- D. Refactor
- E. รีวิวโค้ด
- F. เขียน test
- G. แบบรายงานส่งมอบ

## A. สำรวจโปรเจ็กต์

| ขั้น | ทำอะไร                                                                         | ผลที่ต้องได้                                                     |
| ---- | ------------------------------------------------------------------------------ | ---------------------------------------------------------------- |
| 1    | อ่าน `AGENTS.md`, `CLAUDE.md`, `README` ถ้ามี                                  | รู้กฎเฉพาะของโปรเจ็กต์                                           |
| 2    | อ่านไฟล์ประกาศ dependency (`package.json`, `pyproject.toml`, `platformio.ini`) | รู้ภาษา framework library และคำสั่ง script ที่มี                 |
| 3    | อ่าน config ของ compiler, linter, test                                         | รู้คำสั่ง typecheck / lint / test ที่ใช้จริง                     |
| 4    | ดูโครงสร้างโฟลเดอร์ 2 ระดับ                                                    | รู้ว่าโค้ดจัดกลุ่มอย่างไร                                        |
| 5    | เปิดฟีเจอร์ที่มีอยู่หนึ่งอันที่คล้ายงานนี้ อ่านตั้งแต่ทางเข้าจนถึงฐานข้อมูล    | รู้ convention จริง: ตั้งชื่อ, จัด layer, จัดการ error, validate |
| 6    | ค้นหาว่ามี schema, error class, logger, constant กลางอยู่ที่ไหน                | รายการของที่ต้อง reuse                                           |

เขียนสรุปสั้น ๆ 5–8 บรรทัดก่อนเริ่มงาน ถ้า convention เดิมขัดกับมาตรฐานของเจ้าของ ให้ทำตาม convention เดิมในส่วนที่แตะ และแจ้งเจ้าของถึงจุดที่ขัด ไม่แก้ทั้งโปรเจ็กต์เอง

## B. ฟีเจอร์ใหม่

| ขั้น | ทำอะไร                                                                                            | ผลที่ต้องได้                                   |
| ---- | ------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| 1    | กรอกแบบสรุปโจทย์ใน [thinking.md](thinking.md)                                                     | เป้าหมาย ขอบเขต เกณฑ์สำเร็จที่ตรวจได้          |
| 2    | ทำ playbook A ถ้ายังไม่ได้ทำ                                                                      | รายการของที่ reuse                             |
| 3    | ออกแบบ flow ตาม [project-flow.md](project-flow.md) รวมเส้นทางผิดพลาด                              | flow เป็นข้อความหรือแผนภาพ                     |
| 4    | เขียน constant และ schema: input, output, แถวฐานข้อมูล                                            | ไฟล์ schema ที่ typecheck ผ่าน                 |
| 5    | ออกแบบตาราง: คอลัมน์ key constraint index และ migration ถ้าต้องมี                                 | SQL หรือไฟล์ migration ยังไม่รันกับ production |
| 6    | เขียน repository พร้อม validate ผลจากฐานข้อมูล                                                    | ฟังก์ชัน query ที่ใช้ parameter ทั้งหมด        |
| 7    | เขียนกฎธุรกิจเป็น pure function และ test ของมัน                                                   | test ผ่าน                                      |
| 8    | เขียน service ประสานงาน รวม idempotency และ transaction                                           | กรณีส่งซ้ำและทำพร้อมกันมีคำตอบ                 |
| 9    | เขียน handler: auth → validate → service → response                                               | endpoint หรือทางเข้าที่เรียกได้                |
| 10   | เพิ่ม log, trace id ตามระบบเดิม และปรับ API spec                                                  | spec ตรงกับโค้ด                                |
| 11   | รัน typecheck, lint, test ทั้งหมดที่เกี่ยว และ `node <skill>/scripts/check-code.mjs <ไฟล์ที่แก้>` | ผลรันจริงทุกคำสั่ง ไม่มี `[error]`             |
| 12   | ตรวจตาม [review-checklist.md](review-checklist.md) แล้วเขียนรายงาน                                | รายงานตามแบบ G                                 |

หยุดถามเจ้าของก่อนทำต่อเมื่อ: ต้องเพิ่ม package, ต้องเปลี่ยน schema ของตารางที่มีข้อมูลอยู่, ต้องเปลี่ยน contract ที่มีผู้ใช้เดิม, หรือเกณฑ์สำเร็จตีความได้สองทาง

## C. แก้บั๊ก

| ขั้น | ทำอะไร                                                                | ผลที่ต้องได้                                                |
| ---- | --------------------------------------------------------------------- | ----------------------------------------------------------- |
| 1    | เขียนให้ชัด: ทำอะไร คาดว่าเกิดอะไร เกิดอะไรจริง                       | ประโยคสามส่วน                                               |
| 2    | ทำให้เกิดซ้ำ ด้วย test หรือขั้นตอนที่ทำตามได้                         | วิธีทำซ้ำที่ได้ผลทุกครั้ง หรือบันทึกว่าทำซ้ำไม่ได้เพราะอะไร |
| 3    | อ่าน error และ stack trace ทั้งหมด หาบรรทัดแรกที่เป็นโค้ดของโปรเจ็กต์ | จุดเริ่มค้น                                                 |
| 4    | ไล่ข้อมูลย้อนจากจุดที่พังไปหาจุดที่ค่าเริ่มผิด                        | บรรทัดที่เป็นสาเหตุต้นทาง                                   |
| 5    | อธิบายสาเหตุเป็นหนึ่งประโยค "พังเพราะ ... เมื่อ ..."                  | คำอธิบายที่ทำนายอาการได้ทุกข้อ                              |
| 6    | เขียน test ที่ล้มเหลวเพราะบั๊กนี้                                     | test แดง                                                    |
| 7    | แก้ที่สาเหตุ ด้วยการเปลี่ยนที่เล็กที่สุด                              | test เขียว                                                  |
| 8    | รัน test ทั้งชุด typecheck และ `scripts/check-code.mjs` กับไฟล์ที่แก้ | ไม่มีอะไรพังเพิ่ม                                           |
| 9    | ค้นหารูปแบบเดียวกันในที่อื่นของโค้ด                                   | รายการจุดที่มีปัญหาเดียวกัน แจ้งเจ้าของ ไม่แก้นอก scope เอง |

ถ้าอธิบายขั้น 5 ไม่ได้ แปลว่ายังไม่เจอสาเหตุ ห้ามแก้แบบลองไปเรื่อย ๆ ให้กลับไปขั้น 4 และเพิ่ม log ชั่วคราวเพื่อดูค่าจริง แล้วลบ log นั้นออกก่อนส่ง

สมมติฐานที่ควรตรวจก่อนเมื่อยังหาไม่เจอ: ค่าเป็น null/undefined, ชนิดข้อมูลไม่ตรง (string กับ number), ลืม await, ลำดับการทำงานไม่ใช่อย่างที่คิด, ข้อมูลในฐานข้อมูลไม่ตรงกับที่ schema คาด, เขตเวลา, config ของ environment ต่างกัน, cache ค้าง

## D. Refactor

1. ระบุเป้าหมายเป็นประโยคเดียว และยืนยันว่าเจ้าของขอ refactor ส่วนนี้
2. ตรวจว่ามี test คลุมพฤติกรรมปัจจุบัน ถ้าไม่มีให้เขียน test ที่ยึดพฤติกรรมเดิมก่อน
3. เปลี่ยนทีละก้าวเล็ก แต่ละก้าวไม่เปลี่ยนพฤติกรรม แล้วรัน test ทุกก้าว
4. ไม่ผสมการเปลี่ยนพฤติกรรมหรือแก้บั๊กใน refactor เดียวกัน ถ้าเจอบั๊กให้จดแล้วแจ้ง
5. ตรวจว่า contract ภายนอก (ชื่อ export, รูปร่าง response, ชื่อคอลัมน์) ไม่เปลี่ยน

## E. รีวิวโค้ด

อ่านตามลำดับนี้ เพราะปัญหาช่วงบนมีผลร้ายแรงกว่าและทำให้ข้อสังเกตช่วงล่างหมดความหมายถ้าต้องเขียนใหม่:

1. **เข้าใจเจตนา:** โค้ดนี้ตั้งใจทำอะไร อ่านคำอธิบายและ test ก่อน
2. **ความถูกต้อง:** ทำตามเจตนาหรือไม่ ไล่กรณีปกติหนึ่งและกรณีขอบสองกรณีด้วยมือ
3. **ความปลอดภัย:** ตรวจสิทธิ์, injection, ข้อมูลลับใน response หรือ log
4. **ข้อมูล:** validate ที่ขอบเขต, transaction, idempotency, การทำพร้อมกัน, migration
5. **Error และ async:** error ถูกกลืนหรือไม่ promise ลอยหรือไม่
6. **ประสิทธิภาพ:** N+1, ไม่มี pagination, query ไม่ใช้ index
7. **มาตรฐาน:** กฎ 16 ข้อที่เหลือ
8. **ความอ่านง่าย:** ชื่อ, ความซับซ้อนเกินจำเป็น

รายงานแต่ละข้อด้วยรูปแบบนี้ เรียงจากรุนแรงที่สุด:

```text
[ระดับ] ไฟล์:บรรทัด — ปัญหาในหนึ่งประโยค
เกิดอะไรขึ้น: input หรือสถานการณ์ที่ทำให้พัง และผลที่ตามมา
แนะนำ: วิธีแก้ที่เจาะจง
```

ระดับ: **ต้องแก้** (ผิด, ไม่ปลอดภัย, ข้อมูลเสียหาย) / **ควรแก้** (ขัดมาตรฐาน, เสี่ยงในอนาคตอันใกล้) / **เสนอแนะ** (อ่านง่ายขึ้น) รายงานเฉพาะสิ่งที่ยืนยันได้จากโค้ด ถ้าไม่แน่ใจให้เขียนเป็นคำถาม ไม่มีปัญหาก็บอกว่าไม่พบ ไม่ต้องหาเรื่องมาเติม

## F. เขียน test

1. เลือกสิ่งที่จะทดสอบจากพฤติกรรม ไม่ใช่จากบรรทัดโค้ด: กฎธุรกิจ, การแปลงข้อมูล, เงื่อนไขสิทธิ์, เส้นทางผิดพลาด
2. สำหรับแต่ละพฤติกรรม ไล่กรณีตามรายการ: ปกติ, ค่าขอบ (ศูนย์, หนึ่ง, ค่าสูงสุด, พอดีเส้น), ค่าว่าง, ค่าผิดรูปแบบ, ไม่มีสิทธิ์, ซ้ำ
3. โครงสร้างสามส่วน: เตรียมข้อมูล → เรียกสิ่งที่ทดสอบ → ตรวจผล หนึ่ง test ตรวจหนึ่งพฤติกรรม
4. ชื่อ test บอกเงื่อนไขและผลที่คาด
5. Pure function ทดสอบตรง ๆ Service ทดสอบด้วย repository ปลอมที่เขียนเองแบบง่าย Repository ทดสอบกับฐานข้อมูลทดสอบถ้าโปรเจ็กต์มี
6. test ต้องล้มเหลวได้จริง: ลองทำให้โค้ดผิดชั่วคราวแล้วดูว่า test แดง จากนั้นคืนค่าเดิม

## G. แบบรายงานส่งมอบ

```text
สรุป: ทำอะไรเสร็จ หนึ่งถึงสองประโยค

สิ่งที่เปลี่ยน
- path/ไฟล์ — เปลี่ยนอะไร เพราะอะไร

การตัดสินใจสำคัญ
- เลือก X แทน Y เพราะ ...

ผลตรวจที่รันจริง
- <คำสั่ง> → ผ่าน / ไม่ผ่าน (รายละเอียด)

ยังไม่ได้ตรวจ
- ... เพราะ ...

สมมติฐานและคำถามถึงเจ้าของ
- ...
```
