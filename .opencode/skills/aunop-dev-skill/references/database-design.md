# ออกแบบฐานข้อมูลและ migration

ใช้เมื่อเพิ่มหรือเปลี่ยนตาราง คอลัมน์ index หรือเขียน query ที่ไม่ใช่การอ่านธรรมดา กฎการตั้งชื่ออยู่ใน [coding-standards.md](coding-standards.md) เจ้าของใช้ฐานข้อมูลหลายตัวแล้วแต่โปรเจ็กต์ ขั้นแรกจึงต้องตรวจว่าโปรเจ็กต์ใช้ตัวใดและเวอร์ชันใด ตัวอย่างในไฟล์นี้ใช้ไวยากรณ์ PostgreSQL เป็นแบบ ชนิดข้อมูลและคำสั่ง (`uuid`, `timestamptz`, `ON CONFLICT`, `RETURNING`, `CREATE INDEX CONCURRENTLY`) ต่างกันในฐานข้อมูลอื่น ให้แปลงเป็นของตัวที่โปรเจ็กต์ใช้ และถ้าใช้ ORM ให้ใช้รูปแบบของ ORM นั้น และเปิดดู migration เดิมของโปรเจ็กต์เป็นแบบ

ไฟล์นี้ไม่อนุญาตให้รัน migration กับ production การรันกับข้อมูลจริงต้องได้คำสั่งจากเจ้าของทุกครั้ง

## ขั้นตอนออกแบบตาราง

1. ลิสต์สิ่งที่ต้องเก็บจาก flow: แต่ละ "สิ่ง" ที่มีตัวตนและวงจรชีวิตของตัวเองเป็นหนึ่งตาราง
2. ลิสต์คำถามที่ระบบจะถามข้อมูลนี้ (หน้าจอและ API ไหนอ่านอะไร กรองและเรียงด้วยอะไร) รายการนี้กำหนด index
3. กรอกตารางคอลัมน์ด้านล่าง
4. กำหนด constraint ให้ฐานข้อมูลบังคับกฎที่ต้องเป็นจริงเสมอ
5. กำหนด index จากคำถามในข้อ 2
6. เขียน schema ของแถวให้ตรงกับตาราง ตาม [code-examples.md](code-examples.md) หัวข้อ 2
7. เขียน migration ตามหัวข้อ "Migration ที่ปลอดภัย"

## ตัวอย่าง

```sql
CREATE TABLE leave_request_tb (
  leave_request_id          uuid        PRIMARY KEY,
  leave_request_user_id     uuid        NOT NULL REFERENCES user_tb (user_id),
  leave_request_status      text        NOT NULL
    CHECK (leave_request_status IN ('PENDING', 'APPROVED', 'REJECTED', 'CANCELLED')),
  leave_request_start_date  date        NOT NULL,
  leave_request_end_date    date        NOT NULL,
  leave_request_reason      text        NOT NULL DEFAULT '',
  leave_request_idempotency_key text    NOT NULL,
  leave_request_create_date  timestamptz NOT NULL DEFAULT now(),
  leave_request_update_date  timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT leave_request_date_order_ck
    CHECK (leave_request_end_date >= leave_request_start_date),
  CONSTRAINT leave_request_idempotency_key_uq
    UNIQUE (leave_request_idempotency_key)
);

-- หน้ารายการคำขอของฉัน: กรองด้วยผู้ใช้ เรียงจากใหม่ไปเก่า
CREATE INDEX leave_request_user_created_ix
  ON leave_request_tb (leave_request_user_id, leave_request_create_date DESC);
```

ค่าสถานะใน `CHECK` ต้องตรงกับ constant ในโค้ด เมื่อเพิ่มสถานะต้องแก้ทั้งสองที่ใน migration เดียวกับการเปลี่ยนโค้ด

## กฎเลือกชนิดข้อมูล

| ข้อมูล | ใช้ | เหตุผล |
| --- | --- | --- |
| รหัสหลัก | `uuid` หรือชนิดที่โปรเจ็กต์ใช้อยู่ | เดาไม่ได้และสร้างได้จากฝั่งแอป ทำตามของเดิมถ้ามี |
| เงิน | จำนวนเต็มหน่วยย่อย (`bigint` สตางค์) หรือ `numeric` | เลขทศนิยมแบบ float คลาดเคลื่อน |
| เวลาที่เกิดเหตุการณ์ | `timestamptz` เก็บเป็น UTC | แปลงเขตเวลาตอนแสดงผล |
| วันที่ไม่มีเวลา (วันเกิด, วันลา) | `date` | ไม่ถูกเลื่อนวันเพราะเขตเวลา |
| สถานะ, ประเภท | `text` + `CHECK` หรือ enum ของฐานข้อมูล | บังคับค่าที่อนุญาต |
| ใช่/ไม่ใช่ | `boolean NOT NULL` | สามสถานะ (จริง เท็จ ว่าง) ทำให้เงื่อนไขผิดง่าย |
| ข้อความ | `text` + `CHECK` ความยาวเมื่อมีขีดจำกัด | |
| ข้อมูลโครงสร้างไม่แน่นอน | `jsonb` เฉพาะเมื่อไม่ต้องกรองหรือ join ด้วยข้อมูลข้างใน | ข้อมูลที่ต้องค้นควรเป็นคอลัมน์ |

## Constraint

กฎที่ต้องเป็นจริงเสมอให้ฐานข้อมูลบังคับ เพราะโค้ดมีหลายทางเข้าและมีคำขอพร้อมกัน ส่วนฐานข้อมูลเป็นด่านสุดท้ายด่านเดียว

- `NOT NULL` เป็นค่าตั้งต้นของทุกคอลัมน์ อนุญาตให้ว่างเฉพาะเมื่อ "ไม่มีค่า" มีความหมายจริง
- `UNIQUE` กับทุกอย่างที่ห้ามซ้ำ: อีเมล, idempotency key, คู่ค่าที่ห้ามซ้ำกัน
- `REFERENCES` กับทุกคอลัมน์ที่ชี้ไปตารางอื่น และตัดสินใจว่าลบแม่แล้วลูกเป็นอย่างไร (ห้ามลบ, ลบตาม, ตั้งเป็นว่าง)
- `CHECK` กับช่วงค่าและความสัมพันธ์ระหว่างคอลัมน์

## Index

- สร้างจากคำถามจริง: คอลัมน์ใน `WHERE`, `JOIN` และ `ORDER BY` ของ query ที่เรียกบ่อย
- Index หลายคอลัมน์: คอลัมน์ที่เทียบด้วยเท่ากับมาก่อน คอลัมน์ที่เรียงหรือเทียบช่วงมาทีหลัง
- คอลัมน์ foreign key ที่ใช้ join หรือกรอง ต้องมี index
- ไม่สร้างเผื่อ ทุก index ทำให้การเขียนช้าลง
- query สำคัญให้ดูแผนการทำงานด้วย `EXPLAIN` ถ้ามีฐานข้อมูลทดสอบ ถ้าไม่มีให้ระบุว่ายังไม่ได้ตรวจ

## Transaction

ใช้เมื่อหลายคำสั่งเขียนต้องสำเร็จหรือล้มเหลวพร้อมกัน

- ขอบเขตสั้นที่สุด: เปิด ทำงานกับฐานข้อมูล ปิด
- ห้ามเรียกระบบภายนอก (HTTP, ส่งอีเมล) ระหว่าง transaction เปิดอยู่ เพราะถือ lock นานและย้อนผลภายนอกไม่ได้ ให้บันทึกงานที่ต้องทำไว้ในตารางใน transaction เดียวกัน แล้วให้ตัวประมวลผลแยกส่งทีหลัง
- อ่านแล้วเขียนตามค่าที่อ่าน ต้องกันการแทรก: ใส่เงื่อนไขค่าเดิมใน `UPDATE`, ใช้ `SELECT ... FOR UPDATE`, หรือใช้ unique constraint
- ล็อกหลายแถวให้ล็อกตามลำดับเดียวกันเสมอ เพื่อไม่ให้ deadlock

## Migration ที่ปลอดภัย

หลักการ: โค้ดรุ่นเก่าและรุ่นใหม่ต้องทำงานกับฐานข้อมูลได้พร้อมกันในช่วง deploy การเปลี่ยนแบบทำลายจึงแบ่งเป็นหลายรอบ

| ต้องการ | ลำดับที่ปลอดภัย |
| --- | --- |
| เพิ่มคอลัมน์บังคับ | เพิ่มแบบว่างได้หรือมีค่าเริ่มต้น → เติมข้อมูลเก่า → โค้ดเขียนค่าเสมอ → ตั้ง `NOT NULL` |
| เปลี่ยนชื่อคอลัมน์ | เพิ่มคอลัมน์ใหม่ → โค้ดเขียนทั้งสอง → คัดลอกข้อมูลเก่า → โค้ดอ่านจากใหม่ → เลิกเขียนเก่า → ลบเก่า |
| ลบคอลัมน์ | โค้ดเลิกอ่านและเขียน → deploy → ลบคอลัมน์ |
| เปลี่ยนชนิด | เหมือนเปลี่ยนชื่อ: คอลัมน์ใหม่ชนิดใหม่ แล้วย้าย |
| เพิ่ม index ในตารางใหญ่ | ใช้วิธีที่ไม่ล็อกการเขียน (`CREATE INDEX CONCURRENTLY` ใน PostgreSQL) |
| เพิ่ม unique constraint | ตรวจและแก้ข้อมูลซ้ำที่มีอยู่ก่อน |

ทุก migration:

- [ ] ทำตามรูปแบบและเครื่องมือ migration ของโปรเจ็กต์
- [ ] มีทางย้อนกลับ หรือระบุว่าย้อนไม่ได้เพราะอะไร
- [ ] ไม่แก้ไฟล์ migration ที่เคยรันไปแล้ว ให้เพิ่มไฟล์ใหม่
- [ ] การเติมข้อมูลจำนวนมากทำเป็นชุด ไม่ใช่คำสั่งเดียวทั้งตาราง
- [ ] ไม่เปลี่ยนชื่อหรือลบของที่โค้ดรุ่นปัจจุบันยังใช้
- [ ] แจ้งเจ้าของถึงผลกระทบ: ล็อกตารางหรือไม่ ใช้เวลาประมาณไหน ต้องรันก่อนหรือหลัง deploy โค้ด
- [ ] ทดสอบรันกับฐานข้อมูลทดสอบ หรือระบุว่ายังไม่ได้รัน

## ตรวจ query ก่อนส่ง

- [ ] ค่าจากผู้ใช้ผ่าน parameter ทั้งหมด
- [ ] ระบุคอลัมน์ ไม่ใช้ `SELECT *`
- [ ] query ที่คืนหลายแถวมี `LIMIT` และ `ORDER BY` ที่ไม่กำกวม
- [ ] ไม่มี query ในลูป
- [ ] `UPDATE` และ `DELETE` มี `WHERE` ที่เจาะจง
- [ ] เงื่อนไขใช้ index ได้ ไม่ครอบคอลัมน์ด้วยฟังก์ชัน และไม่ขึ้นต้น `LIKE` ด้วย `%`
- [ ] ผลลัพธ์ผ่าน schema ก่อนใช้
