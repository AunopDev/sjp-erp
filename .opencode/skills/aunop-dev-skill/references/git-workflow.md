# Git และการ commit

ใช้เมื่อเจ้าของขอให้ commit, สร้าง branch, เปิด pull request หรือเขียนข้อความ commit ถ้าโปรเจ็กต์มีรูปแบบของตัวเอง (ดูจาก `git log` ล่าสุด 10–20 รายการ และไฟล์ CONTRIBUTING) ให้ทำตามรูปแบบนั้นก่อน

## ขอบเขตที่ทำได้

- commit และ push เฉพาะเมื่อเจ้าของขอ การแก้ไฟล์เสร็จไม่ใช่คำขอให้ commit
- ไม่ commit ลง branch หลักโดยตรง ถ้าอยู่บน branch หลักให้สร้าง branch ก่อน
- คำสั่งที่ทำให้งานหายหรือเขียนทับประวัติ ต้องได้คำสั่งชัดเจนจากเจ้าของทุกครั้ง: `push --force`, `reset --hard`, `clean -fd`, `checkout -- <ไฟล์>`, `branch -D`, `rebase` บน branch ที่ push แล้ว
- ไม่ข้าม hook ด้วย `--no-verify` ถ้า hook ไม่ผ่านให้แก้สาเหตุ
- ไม่แก้การตั้งค่า git ของเครื่อง

## ขั้นตอน commit

| ขั้น | คำสั่ง | ดูอะไร |
| --- | --- | --- |
| 1 | `git status` | อยู่ branch ไหน ไฟล์ไหนเปลี่ยน มีไฟล์ที่ไม่รู้จักหรือไม่ |
| 2 | `git diff` | อ่านทุกบรรทัดที่เปลี่ยน ตรงกับงานที่ขอหรือไม่ |
| 3 | รัน typecheck, lint, test ของโปรเจ็กต์ | ผ่านทั้งหมด |
| 4 | `git add <ไฟล์ที่เกี่ยว>` | ระบุไฟล์เอง ไม่ใช้ `git add .` หรือ `-A` |
| 5 | `git diff --staged` | สิ่งที่จะ commit ตรงกับที่ตั้งใจ |
| 6 | `git commit` | ข้อความตามรูปแบบด้านล่าง |
| 7 | `git status` และ `git log -1` | commit สำเร็จและไม่มีไฟล์ตกค้างที่ควรรวม |

ในขั้น 2 และ 5 ให้หาสิ่งที่ไม่ควรเข้า commit:

- ความลับ: คีย์, รหัสผ่าน, token, ไฟล์ `.env`, `secrets.h`
- ไฟล์ที่สร้างอัตโนมัติ: โฟลเดอร์ build, `node_modules`, ไฟล์ log
- โค้ด debug: `console.log`, log ชั่วคราว, โค้ดที่ปิดไว้ด้วย comment
- การเปลี่ยนที่ไม่เกี่ยวกับงาน: การจัดรูปแบบทั้งไฟล์, ไฟล์ที่เผลอแก้

เจอไฟล์ที่เปลี่ยนแต่ไม่ได้เป็นคนแก้ ให้ถามเจ้าของ ไม่ commit รวมและไม่ย้อนทิ้ง

## ขนาดของ commit

หนึ่ง commit คือการเปลี่ยนหนึ่งเรื่องที่อธิบายได้ในหนึ่งประโยค และโปรเจ็กต์ยัง build ผ่านหลัง commit นั้น

- แยก refactor ออกจากการเปลี่ยนพฤติกรรม
- แยกการจัดรูปแบบออกจากการแก้โค้ด
- migration อยู่ใน commit เดียวกับโค้ดที่ต้องใช้มัน
- test อยู่ใน commit เดียวกับโค้ดที่มันทดสอบ

## ข้อความ commit

ถ้าโปรเจ็กต์ไม่มีรูปแบบ ให้ใช้รูปแบบนี้:

```text
<ชนิด>(<ขอบเขต>): <สรุปสิ่งที่เปลี่ยน ไม่เกินราว 70 ตัวอักษร>

<ทำไมต้องเปลี่ยน และมีอะไรที่ผู้อ่านควรรู้ เว้นได้ถ้าบรรทัดแรกชัดแล้ว>
```

| ชนิด | ใช้เมื่อ |
| --- | --- |
| `feat` | เพิ่มความสามารถที่ผู้ใช้เห็น |
| `fix` | แก้บั๊ก |
| `refactor` | เปลี่ยนโครงสร้าง พฤติกรรมเท่าเดิม |
| `test` | เพิ่มหรือแก้ test อย่างเดียว |
| `docs` | เอกสารอย่างเดียว |
| `chore` | งานดูแล: การตั้งค่า, dependency, script |
| `perf` | ปรับความเร็วหรือการใช้ทรัพยากร |

บรรทัดแรกบอกสิ่งที่เปลี่ยนในมุมของพฤติกรรม เนื้อหาบอกเหตุผล เขียนเป็นภาษาอังกฤษตาม [owner-profile.md](owner-profile.md) บรรทัดแรกขึ้นต้นด้วยกริยารูปคำสั่ง ตัวพิมพ์เล็ก ไม่มีจุดท้าย

| ไม่ดี | ดี |
| --- | --- |
| `update code` | `fix(leave): return existing result when cancelling twice` |
| `fix bug` | `fix(order): prevent duplicate orders on double submit` |
| `wip` | `feat(leave): add endpoint to cancel pending leave requests` |
| `fix review comments` | `refactor(leave): move cancel rules into a pure function` |

ตัวอย่างที่มีเนื้อหา:

```text
fix(order): prevent duplicate orders on double submit

The old code checked for an existing order before inserting, which does not
stop two requests that arrive at the same time. Use a unique constraint on
order_idempotency_key with INSERT ... ON CONFLICT DO NOTHING and return the
existing order instead.

Run migration 0007 before deploying.
```

## Branch

ถ้าโปรเจ็กต์ไม่มีรูปแบบ ให้ใช้ `<ชนิด>/<คำอธิบายสั้นคั่นด้วยขีด>` เช่น `feat/cancel-leave-request`, `fix/duplicate-order` สร้างจาก branch หลักที่อัปเดตล่าสุด หนึ่ง branch ต่อหนึ่งงาน

## Pull request

หัวข้อใช้รูปแบบเดียวกับบรรทัดแรกของ commit เนื้อหาเขียนเป็นภาษาอังกฤษตามหัวข้อนี้ (ข้อความในวงเล็บแหลมคือคำอธิบายว่าต้องเขียนอะไร):

```text
## What
<สรุปสิ่งที่เปลี่ยนในมุมของผู้ใช้หรือระบบ 2–4 บรรทัด>

## Why
<ปัญหาหรือความต้องการที่นำมาสู่งานนี้>

## How it was tested
- <คำสั่งที่รันและผล>
- <ขั้นตอนทดสอบด้วยมือ ถ้ามี>

## Review focus
- <จุดที่ตัดสินใจยาก หรือยังไม่แน่ใจ>

## Impact
- <migration, การตั้งค่าใหม่, การเปลี่ยน API, ลำดับการ deploy>
```

เปิด pull request เมื่อเจ้าของขอ และ push เฉพาะ branch ของงาน

## เมื่อเกิดปัญหา

| สถานการณ์ | ทำอย่างไร |
| --- | --- |
| merge conflict | เปิดทั้งสองฝั่ง ทำความเข้าใจเจตนาของแต่ละฝั่ง แล้วรวมให้คงเจตนาทั้งคู่ ถ้าตัดสินไม่ได้ให้ถาม ไม่เลือกฝั่งใดฝั่งหนึ่งทิ้งทั้งก้อน หลังแก้ให้รัน test |
| commit ผิดและยังไม่ push | แก้แล้ว commit ใหม่ หรือถามเจ้าของก่อนใช้ `--amend` |
| commit ผิดและ push แล้ว | เพิ่ม commit ที่แก้ หรือ `git revert` ไม่เขียนทับประวัติ |
| commit ความลับไปแล้ว | แจ้งเจ้าของทันที ความลับนั้นต้องเปลี่ยนใหม่ การลบใน commit ถัดไปไม่ทำให้ปลอดภัย |
| hook หรือ CI ไม่ผ่าน | อ่านข้อความทั้งหมด แก้ที่สาเหตุ ไม่ปิดการตรวจ |
| ไม่แน่ใจว่าคำสั่งจะทำอะไร | ไม่รัน ถามเจ้าของ |
