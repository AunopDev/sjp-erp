# งาน IoT และ ESP32

ใช้เมื่อเขียนหรือออกแบบ firmware สำหรับ ESP32 หรือไมโครคอนโทรลเลอร์อื่น และระบบที่รับข้อมูลจากอุปกรณ์ หลักการทั่วไปใน [coding-standards.md](coding-standards.md) ยังใช้ทั้งหมด ไฟล์นี้แปลงเป็นรูปแบบของงานฝังตัว ตัวอย่างใช้ Arduino framework ถ้าโปรเจ็กต์ใช้ ESP-IDF ให้ใช้ API ที่เทียบเท่า

ก่อนเขียน ให้เปิดดู `platformio.ini` หรือการตั้งค่า board และรายการ library ของโปรเจ็กต์ ชื่อฟังก์ชันและพฤติกรรมของ library ต่างกันตามเวอร์ชัน ห้ามเขียนจากความจำ ให้เปิดดูตัวอย่างหรือ header ของ library ที่ติดตั้งอยู่ ไม่เพิ่ม library ใหม่โดยไม่ถาม

## สิ่งที่ต่างจากงานเว็บ

| เรื่อง                      | ผลต่อการออกแบบ                                                             |
| --------------------------- | -------------------------------------------------------------------------- |
| หน่วยความจำจำกัด            | ไม่สร้าง `String` ต่อกันในลูป ใช้ buffer ขนาดคงที่ ตรวจผลการจองหน่วยความจำ |
| ไฟดับและรีเซ็ตได้ทุกเมื่อ   | ทุกขั้นต้องเริ่มใหม่ได้ สถานะสำคัญเก็บลงหน่วยความจำถาวร                    |
| เครือข่ายหลุดเป็นเรื่องปกติ | ทำงานต่อได้แบบออฟไลน์ เก็บคิว แล้วส่งเมื่อกลับมา                           |
| แก้โค้ดในสนามยาก            | ต้องมี watchdog, การกู้คืนตัวเอง และทางอัปเดต                              |
| ทดสอบอัตโนมัติยาก           | แยก logic ออกจาก hardware ให้ทดสอบบนคอมพิวเตอร์ได้                         |
| ใช้พลังงานและความร้อน       | เลือกช่วงเวลาอ่านและส่งให้เหมาะ ใช้ sleep เมื่อใช้แบตเตอรี่                |

## โครงสร้างโค้ด

```text
src/
  config.h          ค่าคงที่: pin, ช่วงเวลา, ขนาด buffer, URL
  secrets.h         ความลับ ไม่ commit (มี secrets.example.h เป็นแบบ)
  main.cpp          setup, loop และการประสานงาน
  <ชื่องาน>_logic.h/.cpp   การตัดสินใจล้วน ๆ ไม่ include Arduino.h
  <อุปกรณ์>_driver.h/.cpp  อ่านเซนเซอร์ ควบคุมอุปกรณ์
  net_client.h/.cpp        WiFi, HTTP หรือ MQTT
```

ไฟล์ logic รับค่าเข้าและคืนผลการตัดสินใจ ไม่เรียก `digitalRead`, `millis`, `WiFi` โดยตรง เวลาปัจจุบันส่งเข้าเป็นพารามิเตอร์ ทำให้ทดสอบบนคอมพิวเตอร์ได้และย้าย board ได้

## Loop ที่ไม่บล็อก

ห้ามใช้ `delay()` ยาวใน loop หลัก เพราะระหว่างนั้นอุปกรณ์ไม่อ่านปุ่ม ไม่รับข้อมูล และไม่ป้อน watchdog ใช้การเทียบเวลา:

```cpp
// config.h
constexpr uint32_t SENSOR_READ_INTERVAL_MS = 2000;
constexpr uint32_t UPLOAD_INTERVAL_MS = 60000;

// main.cpp
static uint32_t lastSensorReadMs = 0;

void loop() {
  const uint32_t nowMs = millis();
  if (nowMs - lastSensorReadMs >= SENSOR_READ_INTERVAL_MS) {
    lastSensorReadMs = nowMs;
    readSensors();
  }
  serviceNetwork(nowMs);
}
```

เขียนเป็น `nowMs - lastMs >= INTERVAL` เสมอ รูปแบบนี้ยังถูกต้องเมื่อ `millis()` วนกลับเป็นศูนย์หลังราว 49 วัน ส่วน `nowMs >= lastMs + INTERVAL` จะผิด

งานที่มีหลายขั้นและต้องรอ ให้เขียนเป็น state machine: ตัวแปรสถานะหนึ่งตัว และ `switch` ที่ทำงานสั้น ๆ ต่อรอบ loop ออกแบบสถานะด้วยตารางใน [system-design.md](system-design.md)

## ข้อมูลเข้าและ buffer

ข้อมูลจาก serial, HTTP, MQTT, QR หรือเซนเซอร์ เป็นข้อมูลภายนอก ตรวจก่อนใช้ทุกครั้ง

- ตรวจความยาวก่อนคัดลอกลง buffer ใช้ `snprintf` และ `strlcpy` ไม่ใช้ `sprintf` และ `strcpy`
- ตรวจว่า parse สำเร็จ ก่อนใช้ค่า
- ตรวจช่วงค่าที่เป็นไปได้ทางกายภาพ ค่าที่อยู่นอกช่วงคือเซนเซอร์ผิดปกติ ไม่ใช่ข้อมูล
- ฟังก์ชันที่ล้มเหลวได้ให้คืนสถานะ และผู้เรียกต้องตรวจทุกครั้ง

```cpp
enum class ParseResult : uint8_t { Ok, TooLong, Malformed, OutOfRange };

ParseResult parseSetpoint(const char* text, size_t length, int16_t& outValue) {
  if (length == 0 || length > SETPOINT_TEXT_MAX_LENGTH) {
    return ParseResult::TooLong;
  }
  char* end = nullptr;
  const long value = strtol(text, &end, 10);
  if (end == text || *end != '\0') {
    return ParseResult::Malformed;
  }
  if (value < SETPOINT_MIN || value > SETPOINT_MAX) {
    return ParseResult::OutOfRange;
  }
  outValue = static_cast<int16_t>(value);
  return ParseResult::Ok;
}
```

## เครือข่าย

- เชื่อมต่อใหม่เองเมื่อหลุด ด้วยการรอที่เพิ่มขึ้นเป็นลำดับและมีเพดาน (เช่น 1, 2, 4 ... สูงสุด 60 วินาที) ไม่วนเชื่อมต่อถี่ ๆ
- ทุกการเรียกเครือข่ายมี timeout
- งานหลักของอุปกรณ์ต้องทำต่อได้ขณะไม่มีเครือข่าย
- ข้อมูลที่ยังส่งไม่ได้เก็บในคิวขนาดจำกัด และกำหนดว่าเมื่อเต็มจะทิ้งรายการเก่าสุดหรือใหม่สุด
- ทุกเหตุการณ์มี id ที่อุปกรณ์สร้าง (เช่น รหัสอุปกรณ์ + ตัวนับที่เก็บถาวร) ส่งซ้ำด้วย id เดิม server ตัดรายการซ้ำด้วย unique constraint
- อุปกรณ์อาจไม่มีเวลาที่ถูกต้อง ให้ซิงก์เวลาเมื่อออนไลน์ และให้ server บันทึกเวลาที่รับไว้ด้วย
- ใช้ HTTPS หรือ MQTT ผ่าน TLS และตรวจใบรับรอง การปิดการตรวจใบรับรองต้องได้รับอนุญาตจากเจ้าของ

## Interrupt และงานพร้อมกัน

- ฟังก์ชัน interrupt สั้นที่สุด: ตั้งค่าธงหรือเก็บค่า แล้วออก ไม่พิมพ์ serial ไม่จองหน่วยความจำ ไม่เรียกเครือข่าย
- ตัวแปรที่ใช้ร่วมระหว่าง interrupt กับ loop ประกาศ `volatile` และอ่านค่าหลายไบต์ภายใต้การปิด interrupt ชั่วคราวหรือกลไกของระบบ
- บน ESP32 ที่ใช้ FreeRTOS: ข้อมูลที่ใช้ร่วมระหว่าง task ป้องกันด้วย mutex หรือส่งผ่าน queue กำหนดขนาด stack ของ task จากการวัด และไม่บล็อก task ที่ดูแล WiFi

## ความทนทาน

- เปิด watchdog และป้อนจากจุดเดียวใน loop หลัก ถ้าค้างอุปกรณ์จะรีเซ็ตเอง
- ตอนเริ่มทำงาน บันทึกสาเหตุการรีเซ็ตครั้งก่อน เพื่อใช้วิเคราะห์ปัญหา
- เขียนหน่วยความจำถาวร (NVS, flash) เฉพาะเมื่อค่าเปลี่ยน เพราะจำนวนครั้งเขียนมีจำกัด
- การอัปเดตหรือเขียนข้อมูลสำคัญ ต้องทนไฟดับกลางคัน: เขียนของใหม่ให้ครบก่อน แล้วค่อยสลับ
- เซนเซอร์อ่านไม่ได้: ลองใหม่จำนวนจำกัด แล้วรายงานสถานะผิดปกติ ไม่ส่งค่าเก่าหรือค่าศูนย์เป็นข้อมูลจริง
- มีสัญญาณบอกสถานะให้คนหน้างานเห็น (ไฟ LED, เสียง) อย่างน้อย: กำลังเชื่อมต่อ, พร้อม, ผิดพลาด

## ความลับและการตั้งค่า

- ชื่อและรหัส WiFi, คีย์ API อยู่ใน `secrets.h` ที่ไม่ commit หรือในหน่วยความจำถาวรที่ตั้งค่าตอนติดตั้ง
- แต่ละอุปกรณ์มีรหัสและคีย์ของตัวเอง คีย์เดียวกันทุกเครื่องหมายความว่าหลุดหนึ่งเครื่องคือหลุดทั้งหมด
- ไม่พิมพ์ความลับออก serial
- server ไม่เชื่อข้อมูลจากอุปกรณ์โดยอัตโนมัติ ตรวจตัวตนอุปกรณ์และ validate ข้อมูลตาม [security.md](security.md)
