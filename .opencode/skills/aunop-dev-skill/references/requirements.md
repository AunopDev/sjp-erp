# แปลงคำขอภาษาง่ายเป็นสเปกละเอียด

เจ้าของสั่งงานด้วยภาษาพูดสั้น ๆ หน้าที่ของสกิลนี้คือแปลงคำขอนั้นเป็นสเปกที่ละเอียดพอให้เอเจนต์ตัวอื่นหรือคนเขียนโค้ดทำงานได้โดยไม่ต้องเดา และถ้ามีจุดที่ไม่เข้าใจ ให้กลับไปถามเจ้าของก่อน ไม่เดาแล้วทำ

ใช้ไฟล์นี้กับทุกงานขนาดกลางขึ้นไป และทุกครั้งที่ต้องส่งงานต่อให้เอเจนต์หรือคนอื่น

## ขั้นตอน

| ขั้น | ทำอะไร | ผลที่ต้องได้ |
| --- | --- | --- |
| 1 | อ่านคำขอ แล้วเขียนใหม่ด้วยคำของตัวเองหนึ่งถึงสองประโยค | ประโยค "เข้าใจว่าต้องการ ..." |
| 2 | หาคำตอบจากโปรเจ็กต์ก่อน: โค้ด เอกสาร AGENTS.md งานที่คล้ายกัน | รายการข้อเท็จจริงที่ยืนยันแล้ว |
| 3 | ไล่ตารางช่องว่างด้านล่าง หาสิ่งที่คำขอไม่ได้บอก | รายการช่องว่าง |
| 4 | แบ่งช่องว่างเป็นสามกลุ่ม: ต้องถาม / ตั้งสมมติฐานได้ / ไม่เกี่ยว | รายการคำถามและรายการสมมติฐาน |
| 5 | ถ้ามีข้อ "ต้องถาม" ให้ถามเจ้าของแล้วรอคำตอบ | คำตอบจากเจ้าของ |
| 6 | เขียนสเปกละเอียดตามแม่แบบ | สเปกที่คนอื่นทำตามได้ |
| 7 | งานใหญ่หรือย้อนยาก: ให้เจ้าของดูสเปกก่อนลงมือ | การยืนยันจากเจ้าของ |

## ตารางช่องว่าง

คำขอสั้น ๆ มักไม่ได้บอกเรื่องเหล่านี้ ไล่ทีละแถวแล้วถามตัวเองว่ารู้คำตอบหรือยัง

| เรื่อง | คำถามที่ต้องมีคำตอบ |
| --- | --- |
| ผู้ใช้ | ใครใช้ มีกี่บทบาท แต่ละบทบาททำอะไรได้ |
| เป้าหมาย | ทำไปเพื่อแก้ปัญหาอะไร รู้ได้อย่างไรว่าสำเร็จ |
| ขอบเขต | รวมอะไร ไม่รวมอะไร ต้องเสร็จทั้งหมดหรือทำเป็นรอบ |
| ข้อมูล | เก็บอะไรบ้าง ช่องไหนบังคับ มีข้อจำกัดอะไร ข้อมูลเดิมมีหรือไม่ |
| กฎ | เงื่อนไขอะไรที่ต้องเป็นจริง ใครอนุมัติ มีขีดจำกัดอะไร |
| กรณีไม่ปกติ | ข้อมูลผิด ซ้ำ ยกเลิก แก้ย้อนหลัง ไม่มีสิทธิ์ แล้วควรเกิดอะไร |
| หน้าจอ | ใช้บนอุปกรณ์อะไร มีหน้าไหนบ้าง มีแบบหรือแบรนด์เดิมหรือไม่ |
| ของเดิม | ต่อกับระบบไหน ใช้ stack อะไร มีอะไรห้ามแตะ |
| ข้อจำกัด | กำหนดเวลา งบ เครื่องมือที่ต้องใช้หรือห้ามใช้ |
| การส่งมอบ | อยากได้อะไรกลับไป: โค้ด แผนภาพ mockup เอกสาร |

## ตัดสินว่าต้องถามหรือไม่

ไล่ตามลำดับ ใช้ข้อแรกที่ตรง:

1. หาคำตอบได้จากโปรเจ็กต์หรือข้อความที่เจ้าของเคยให้ → ไม่ถาม ใช้คำตอบนั้น
2. ไม่เข้าใจว่าเจ้าของหมายถึงอะไร → ถาม
3. ตีความได้หลายทาง และแต่ละทางให้ผลงานต่างกัน → ถาม
4. เป็นการตัดสินใจทางธุรกิจหรือรสนิยมของเจ้าของ (กฎอนุมัติ, ใครมีสิทธิ์, ชื่อที่ผู้ใช้เห็น, สีแบรนด์) → ถาม
5. ย้อนกลับยากหรือกระทบของเดิม (โครงสร้างข้อมูล, ลบหรือเปลี่ยนชื่อ, เลือก tech stack, เพิ่ม package) → ถาม
6. เป็นรายละเอียดที่มีค่าตั้งต้นที่ดีและแก้ทีหลังง่าย (ข้อความปุ่ม, จำนวนต่อหน้า, ลำดับช่อง) → ไม่ถาม เลือกแล้วระบุเป็นสมมติฐาน
7. ทุกคำตอบที่เป็นไปได้ให้ผลงานเหมือนกัน → ไม่ถาม

เมื่อลังเลระหว่างถามกับไม่ถาม ให้ถาม เจ้าของต้องการความแน่ใจมากกว่าความเร็ว แต่ห้ามถามสิ่งที่ตอบเองได้จากข้อ 1 เพราะเป็นการผลักงานกลับไปให้เจ้าของ

## รูปแบบคำถาม

- ภาษาง่ายแบบเดียวกับที่เจ้าของใช้ ไม่ใช้ศัพท์เทคนิคถ้าเลี่ยงได้ ถ้าต้องใช้ให้อธิบายสั้น ๆ
- รวมทุกคำถามในครั้งเดียว ไม่เกิน 4 ข้อ เรียงจากข้อที่กระทบงานมากที่สุด
- แต่ละข้อมีตัวเลือก 2–4 ตัว บอกว่าแนะนำตัวไหนและผลของแต่ละตัว เจ้าของตอบได้ด้วยคำเดียว
- บอกว่าทำไมต้องรู้ ในครึ่งประโยค
- ถ้า session มีเครื่องมือถามแบบตัวเลือก ให้ใช้เครื่องมือนั้น

```text
ก่อนเริ่ม ขอยืนยัน 2 เรื่องครับ

1. "ห้องใหญ่" ที่ต้องอนุมัติ ตัดสินจากอะไร (กำหนดว่าระบบจะเช็กอะไรตอนจอง)
   ก. แอดมินติ๊กเลือกเองเป็นรายห้อง (แนะนำ: ยืดหยุ่น ไม่ต้องแก้ระบบเมื่อเปลี่ยนใจ)
   ข. ห้องที่จุเกินจำนวนคนที่กำหนด

2. ยกเลิกการจองได้ถึงเมื่อไร
   ก. ได้จนถึงเวลาเริ่ม (แนะนำ)
   ข. ต้องยกเลิกล่วงหน้าตามเวลาที่กำหนด

เรื่องอื่นผมตั้งค่าตั้งต้นไว้และจะระบุในสเปกให้ตรวจครับ
```

ไม่ดี: "ช่วยอธิบาย requirement เพิ่มเติมได้ไหมครับ" เพราะกว้างเกินและเจ้าของต้องคิดเองทั้งหมดว่าขาดอะไร

เมื่อได้คำตอบแล้วยังมีจุดไม่ชัด ถามต่อได้อีกรอบ แต่รอบสองควรแคบลง ถ้าถามสองรอบแล้วยังไม่ลงตัว ให้เสนอสเปกฉบับร่างพร้อมสมมติฐานให้เจ้าของแก้ ซึ่งง่ายกว่าตอบคำถามปลายเปิด

## เมื่อถามไม่ได้

ถ้าเจ้าของสั่งว่าไม่ต้องถาม หรืองานรันโดยไม่มีคนเฝ้า: เลือกการตีความที่สมเหตุสมผลที่สุด เขียนไว้บนสุดของผลงานว่าตีความอย่างไร แล้วทำต่อ ยกเว้นการกระทำที่ย้อนไม่ได้และตีความได้หลายทาง ให้เตรียมงานให้พร้อมแล้วหยุดรอ

## แม่แบบสเปกละเอียด

สเปกต้องอ่านเข้าใจได้โดยคนที่ไม่เห็นบทสนทนานี้ ทุกหัวข้อเขียนเป็นข้อความที่ตรวจได้ ไม่ใช้คำว่า "เหมาะสม", "ใช้ง่าย", "เร็ว" โดยไม่บอกว่าวัดอย่างไร

```text
# <ชื่องาน>

## คำขอเดิม
<ข้อความของเจ้าของตามที่พิมพ์มา>

## เข้าใจว่า
<เขียนใหม่ 1–3 ประโยค: ใคร ต้องการอะไร เพื่ออะไร>

## ผู้ใช้และสิทธิ์
- <บทบาท>: ทำ <อะไร> ได้ / ไม่ได้

## ขอบเขต
รวม: ...
ไม่รวม: ...

## พฤติกรรมที่ต้องการ
1. เมื่อ <เหตุการณ์/เงื่อนไข> ระบบ <ทำอะไร> ผลที่เห็นคือ <อะไร>
2. ...

## กรณีไม่ปกติ
| สถานการณ์ | ระบบต้องทำอย่างไร |

## ข้อมูล
| ข้อมูล | ชนิด | บังคับ | ข้อจำกัด |

## หน้าจอ (ถ้ามี)
<รายการหน้าจอ และสิ่งที่แต่ละหน้าต้องทำได้>

## ข้อจำกัดทางเทคนิค
<stack, ของเดิมที่ต้องใช้, สิ่งที่ห้ามทำ, มาตรฐานที่ต้องตาม>

## เกณฑ์ตรวจรับ
- [ ] <ข้อที่ตรวจได้ด้วยการรันหรือการดู>

## ตัดสินใจแล้ว (จากเจ้าของ)
- <คำถาม> → <คำตอบ>

## สมมติฐาน (ยังไม่ได้ยืนยัน)
- ...

## คำถามค้าง
- ...
```

## ตัวอย่าง

คำขอ: "อยากได้หน้าให้ รปภ. สแกน QR ตอนเดินตรวจ"

ช่องว่างที่ต้องถาม: สแกนแล้วต้องบันทึกอะไรนอกจากเวลา (รูป, หมายเหตุ) / ไม่มีเน็ตตรงจุดตรวจแล้วต้องทำงานได้หรือไม่ ช่องว่างที่ตั้งสมมติฐานได้: ใช้บนมือถือ, ต้องล็อกอินก่อน, สแกนจุดเดิมซ้ำภายในหนึ่งนาทีนับครั้งเดียว

หลังได้คำตอบ ("บันทึกหมายเหตุได้ ไม่ต้องมีรูป" และ "ต้องใช้ได้ตอนไม่มีเน็ต") พฤติกรรมในสเปกเขียนแบบนี้:

```text
## พฤติกรรมที่ต้องการ
1. เมื่อ รปภ. เปิดหน้าสแกน ระบบเปิดกล้องหลังและแสดงกรอบเล็ง
2. เมื่ออ่าน QR ของจุดตรวจที่อยู่ในรอบตรวจของวันนี้ ระบบบันทึกจุดตรวจ ผู้ตรวจ และเวลา
   แล้วแสดง "บันทึกจุด <ชื่อจุด> แล้ว" พร้อมช่องหมายเหตุที่ไม่บังคับ
3. เมื่อไม่มีเครือข่าย ระบบเก็บรายการไว้ในเครื่อง แสดงป้าย "รอส่ง 3 รายการ"
   และส่งเองเมื่อกลับมาออนไลน์ โดยไม่เกิดรายการซ้ำ

## กรณีไม่ปกติ
| QR ไม่ใช่ของระบบ | แสดง "QR นี้ไม่ใช่จุดตรวจ" ไม่บันทึก |
| สแกนจุดเดิมซ้ำภายใน 1 นาที | แสดง "บันทึกจุดนี้ไปแล้วเมื่อสักครู่" ไม่บันทึกซ้ำ |
| ไม่อนุญาตให้ใช้กล้อง | อธิบายวิธีเปิดสิทธิ์ และมีช่องกรอกรหัสจุดตรวจด้วยมือ |
```

## ส่งงานต่อให้เอเจนต์หรือคนอื่น

ผู้รับไม่เห็นบทสนทนา ไม่รู้จักโปรเจ็กต์ และไม่รู้ว่าอะไรสำคัญ ข้อความส่งงานต้องมีครบ:

```text
เป้าหมาย: <ทำอะไร เพื่ออะไร ผลลัพธ์จะถูกนำไปใช้อย่างไร>
เสร็จเมื่อ: <เกณฑ์ที่ตรวจได้>
บริบทที่รู้แล้ว: <ข้อเท็จจริง, path ของไฟล์ที่เกี่ยว, สิ่งที่ลองแล้วไม่ได้ผล>
ข้อจำกัด: <ขอบเขตไฟล์ที่แก้ได้, สิ่งที่ห้ามทำ, มาตรฐานที่ต้องตาม พร้อม path ของสกิลนี้>
จุดที่ยาก: <สิ่งที่ทำผิดง่าย และทางที่ดูถูกแต่ผิด>
สิ่งที่ต้องส่งกลับ: <รูปแบบผลลัพธ์ และให้แยกสิ่งที่ตรวจแล้วออกจากสิ่งที่คาดเดา>
ถ้าไม่แน่ใจ: <ให้หยุดถาม หรือให้ตั้งสมมติฐานแล้วระบุ>
```

ผลงานที่ได้กลับมาเป็นข้อมูลที่ต้องตรวจ ไม่ใช่ข้อเท็จจริง ให้ตรวจตามเกณฑ์ "เสร็จเมื่อ" ก่อนรายงานเจ้าของ
