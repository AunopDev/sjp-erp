# เลือก tech stack ให้เหมาะกับงาน

ใช้เมื่อเริ่มโปรเจ็กต์ใหม่ เพิ่มส่วนใหม่ที่ยังไม่มี stack หรือเจ้าของถามว่าควรใช้อะไร การเลือก stack ย้อนยาก จึงต้องเสนอทางเลือกพร้อมเหตุผลให้เจ้าของตัดสิน ไม่เลือกเองแล้วลงมือ

โปรเจ็กต์ที่มี stack อยู่แล้ว ให้ใช้ของเดิม ไม่เสนอเปลี่ยนเว้นแต่เจ้าของถาม หรือของเดิมทำงานที่ขอไม่ได้จริง

ความรู้เรื่องเวอร์ชัน สถานะการดูแล และราคาของเครื่องมือล้าสมัยเร็ว ถ้าค้นข้อมูลปัจจุบันได้ให้ค้นก่อนเสนอ ถ้าค้นไม่ได้ให้บอกเจ้าของว่าข้อมูลมาจากความรู้เดิมและควรตรวจซ้ำ ห้ามระบุเลขเวอร์ชันจากความจำ

## ขั้นตอน

1. เก็บข้อกำหนดตามตารางด้านล่าง ข้อที่ไม่รู้ให้ถามตาม [requirements.md](requirements.md)
2. ระบุสิ่งที่ถูกกำหนดไว้แล้ว: ของที่เจ้าของใช้เป็นอยู่ ของที่โปรเจ็กต์อื่นของเจ้าของใช้ เครื่องและบริการที่มี
3. เลือกผู้สมัคร 2–3 ชุดจากตารางค่าตั้งต้น
4. ให้คะแนนตามเกณฑ์
5. เสนอเจ้าของ: ชุดที่แนะนำ เหตุผล ข้อเสีย และทางเลือกรอง
6. รอเจ้าของยืนยันก่อนสร้างโปรเจ็กต์หรือติดตั้งอะไร

## ข้อกำหนดที่ต้องรู้ก่อนเลือก

| เรื่อง | คำถาม | มีผลต่อ |
| --- | --- | --- |
| ชนิดงาน | เว็บแอป, เว็บเนื้อหา, แอปมือถือ, API, อุปกรณ์, สคริปต์ | ทั้งชุด |
| ผู้ใช้ | กี่คน ใช้พร้อมกันเท่าไร ภายในองค์กรหรือสาธารณะ | ความจำเป็นของการขยายระบบ |
| อุปกรณ์ | มือถือ คอม หรือทั้งคู่ ต้องติดตั้งเป็นแอปหรือไม่ | frontend |
| ออฟไลน์ | ต้องใช้ได้ตอนไม่มีเน็ตหรือไม่ | frontend, การเก็บข้อมูล |
| ข้อมูล | มีความสัมพันธ์ซับซ้อนหรือไม่ ปริมาณเท่าไร ต้องค้นแบบไหน | ฐานข้อมูล |
| เรียลไทม์ | ต้องอัปเดตทันทีหรือไม่ | โปรโตคอล |
| คนดูแล | ใครดูแลต่อ ถนัดอะไร | ทั้งชุด |
| ที่รัน | เครื่องตัวเอง, คลาวด์, โฮสติ้งที่มีอยู่ งบเท่าไร | การ deploy |
| อายุงาน | ต้นแบบทดลอง หรือระบบที่ใช้ยาว | ความเข้มของโครงสร้าง |
| ต่อกับอะไร | ระบบเดิม อุปกรณ์ บริการภายนอก | ภาษาและ library |

## เกณฑ์ให้คะแนน

เรียงตามน้ำหนัก ข้อบนสำคัญกว่า

1. **ทำงานที่ต้องการได้ครบ** โดยไม่ต้องฝืนเครื่องมือ
2. **เจ้าของและทีมดูแลต่อได้** เครื่องมือที่คุ้นเคยชนะเครื่องมือที่ดีกว่าเล็กน้อยแต่ไม่มีใครเป็น
3. **เข้ากับของที่มีอยู่** ภาษาเดียวกัน ใช้ schema และ type ร่วมกันได้
4. **มั่นคง** มีผู้ใช้มาก เอกสารดี ยังมีการดูแล
5. **เรียบง่าย** จำนวนชิ้นส่วนและบริการน้อยที่สุดที่ตอบโจทย์
6. **ต้นทุน** ค่าบริการและแรงที่ใช้ดูแล

สิ่งที่ไม่ใช่เหตุผล: ใหม่กว่า, กำลังเป็นที่นิยม, รองรับผู้ใช้ระดับล้านคนในงานที่มีผู้ใช้ร้อยคน

## ค่าตั้งต้นตามชนิดงาน

เจ้าของไม่มี stack ประจำ ให้เสนอทางเลือกทุกโปรเจ็กต์ ตารางนี้เป็นจุดเริ่มสำหรับเลือกผู้สมัคร ไม่ใช่คำตอบ สิ่งที่เจ้าของกำหนดไว้แน่นอนคือมาตรฐานโค้ดและโครงสร้างไฟล์แนว Angular และ NestJS ดู [owner-profile.md](owner-profile.md)

| ชนิดงาน | ชุดที่เสนอก่อน | เลือกอย่างอื่นเมื่อ |
| --- | --- | --- |
| เว็บแอปที่มีฟอร์มและตารางมาก ใช้ยาว | Angular + NestJS + PostgreSQL | ทีมถนัด React หรือ Vue อยู่แล้ว |
| API อย่างเดียว | NestJS + PostgreSQL | เล็กมากมีไม่กี่ endpoint: ใช้ framework ที่เบากว่า |
| เว็บเนื้อหาที่ต้องให้ค้นเจอ | framework ที่ render ฝั่ง server หรือสร้างหน้าคงที่ | เป็นแอปหลังล็อกอิน: ไม่จำเป็น |
| ต้นแบบทดลองความคิด | ชิ้นส่วนน้อยที่สุด: frontend เดียวกับของจริง + ฐานข้อมูลไฟล์เดียวอย่าง SQLite | รู้แน่ว่าจะใช้จริงต่อ: เริ่มด้วยชุดจริง |
| แอปมือถือ | เว็บ responsive หรือ PWA ก่อน | ต้องใช้ความสามารถของเครื่องที่เว็บทำไม่ได้: แอป native หรือ cross-platform |
| อุปกรณ์ IoT | ESP32 + PlatformIO ส่งข้อมูลผ่าน HTTPS หรือ MQTT เข้า API เดียวกับเว็บ | ดู [iot-esp32.md](iot-esp32.md) |
| อัปเดตเรียลไทม์ | เริ่มจากการดึงข้อมูลเป็นช่วง ถ้าไม่พอใช้ server-sent events แล้วจึง WebSocket | ต้องสื่อสารสองทางถี่ ๆ: WebSocket |
| งานตามเวลาหรือสคริปต์ | ภาษาเดียวกับระบบหลัก | งานวิเคราะห์ข้อมูล: Python |

ฐานข้อมูล:

| สถานการณ์ | เลือก |
| --- | --- |
| ข้อมูลธุรกิจทั่วไป มีความสัมพันธ์ ต้องการความถูกต้อง | ฐานข้อมูลเชิงสัมพันธ์ เสนอตัวเลือก (PostgreSQL, MySQL/MariaDB, SQL Server) ให้เจ้าของเลือกตามที่มีและที่ดูแลได้ |
| แอปเล็กเครื่องเดียว หรือต้นแบบ | SQLite |
| โครงสร้างข้อมูลไม่แน่นอนจริง ๆ และไม่ต้อง join | คอลัมน์ JSON ในฐานข้อมูลเชิงสัมพันธ์ก่อน แล้วจึงพิจารณาฐานข้อมูลเอกสาร |
| ค่าที่อ่านบ่อยและหายได้ | cache เพิ่มเมื่อวัดแล้วว่าช้า ไม่ใส่ตั้งแต่แรก |
| ไฟล์และรูป | ที่เก็บไฟล์แยก เก็บเฉพาะ path ในฐานข้อมูล |

เริ่มเป็นระบบเดียว (monolith) ที่แบ่งโมดูลชัดเจน แยกเป็นหลายบริการเมื่อมีเหตุผลที่วัดได้ เช่น ส่วนหนึ่งต้องขยายแยก หรือทีมต้อง deploy แยกกัน

## เลือก library

ก่อนเสนอ package ใหม่ (ต้องได้รับอนุญาตจากเจ้าของเสมอ):

- [ ] ของที่มีในโปรเจ็กต์หรือในภาษาทำได้อยู่แล้วหรือไม่
- [ ] เขียนเองสั้น ๆ ได้หรือไม่ โดยไม่ใช่งานที่ต้องอาศัยความเชี่ยวชาญ (ความปลอดภัย, วันเวลา, การเข้ารหัส ควรใช้ library)
- [ ] ยังมีการดูแล: ตรวจวันที่ออกรุ่นล่าสุดและปัญหาที่เปิดค้าง
- [ ] มีผู้ใช้มากพอ และเอกสารอ่านรู้เรื่อง
- [ ] สัญญาอนุญาตใช้กับงานนี้ได้
- [ ] ขนาดและจำนวน dependency ที่ลากมาสมเหตุสมผล
- [ ] เข้ากับเวอร์ชันของ runtime และ framework ที่โปรเจ็กต์ใช้

## รูปแบบข้อเสนอ

```text
งาน: <สรุปหนึ่งประโยค>
ข้อกำหนดที่ใช้ตัดสิน: <3–5 ข้อที่มีน้ำหนักที่สุด>

แนะนำ: <frontend> + <backend> + <ฐานข้อมูล> + <ที่รัน>
เหตุผล:
- <ผูกกับข้อกำหนดข้างบน>
ข้อเสียที่ต้องยอมรับ:
- ...

ทางเลือกรอง: <ชุด> เหมาะกว่าเมื่อ <เงื่อนไข>
ทางที่ไม่แนะนำ: <ชุด> เพราะ <เหตุผล>

ยังไม่ได้ตรวจ: <เช่น เวอร์ชันปัจจุบัน ราคาโฮสติ้ง>
ต้องการให้เจ้าของยืนยัน: <สิ่งที่ต้องตัดสิน>
```

## สัญญาณว่าเลือกซับซ้อนเกิน

- จำนวนบริการที่ต้องรันมากกว่าจำนวนคนดูแล
- มีชิ้นส่วนที่อธิบายไม่ได้ว่าแก้ปัญหาอะไรของงานนี้
- ต้องใช้สองภาษาโดยไม่มีเหตุจำเป็น
- ใส่ cache, คิว, หรือแยกบริการ ก่อนมีตัวเลขว่าช้าหรือรับไม่ไหว
- ตั้งค่าโครงสร้างนานกว่าเขียนฟีเจอร์แรก
