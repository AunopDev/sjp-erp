# วิธีคิดเชิงลึก

ไฟล์นี้คือวิธีทำงานแบบ "คิดให้สุดก่อนตอบ" ใช้กับทุกโหมดงาน เป้าหมายไม่ใช่คิดนานขึ้น แต่คือไม่ส่งงานที่ยังมีจุดที่ตัวเองไม่ได้ตรวจ ความผิดพลาดส่วนใหญ่ไม่ได้มาจากความรู้ไม่พอ แต่มาจากการเดาแทนการดู และการหยุดที่คำตอบแรกที่ดูใช้ได้

## ปรับระดับความลึกตามขนาดงาน

| ขนาดงาน | ตัวอย่าง | ทำขั้นไหน |
| --- | --- | --- |
| เล็ก | แก้ typo, ปรับข้อความ, คำถามข้อเท็จจริง | ขั้น 1, 2, 6 แบบสั้น |
| กลาง | ฟีเจอร์เดียว, แก้บั๊ก, หน้าจอเดียว, flow เดียว | ทุกขั้น เขียนสั้น ๆ |
| ใหญ่ | ระบบใหม่, เปลี่ยนสถาปัตยกรรม, หลายหน้าจอ, ย้ายข้อมูล | ทุกขั้นแบบเต็ม และเขียนแผนให้เจ้าของเห็นก่อนลงมือ |

งานเล็กที่ทำพิธีเต็มรูปแบบเสียเวลาเจ้าของพอ ๆ กับงานใหญ่ที่ข้ามขั้นตอน ถ้าไม่แน่ใจขนาด ให้ดูว่าถ้าผิดแล้วย้อนกลับยากแค่ไหน ยิ่งย้อนยากยิ่งต้องลึก

## ขั้นตอน

### 1. เข้าใจโจทย์ที่แท้จริง

เขียนใหม่ด้วยคำของตัวเองว่า ใครต้องการอะไร เพื่ออะไร และ "เสร็จ" หน้าตาเป็นอย่างไร คำขอมักบอกวิธีแก้ที่ผู้ใช้นึกออก ไม่ใช่ปัญหาจริง จึงควรถามตัวเองว่าเบื้องหลังคำขอนี้คือปัญหาอะไร แยกสามอย่างให้ชัด:

- ข้อเท็จจริง: สิ่งที่เห็นจากโค้ด เอกสาร หรือคำพูดของเจ้าของ
- สมมติฐาน: สิ่งที่คิดว่าน่าจะใช่แต่ยังไม่ได้ตรวจ
- คำถามค้าง: สิ่งที่ต้องให้เจ้าของตัดสิน

### 2. ดูของจริงก่อนเชื่อความจำ

อ่านโค้ด ไฟล์ config schema และผลรันจริง ก่อนสรุปว่าระบบทำงานอย่างไร ความจำเรื่องชื่อฟังก์ชัน พารามิเตอร์ หรือเวอร์ชันของ library ผิดได้เสมอ ถ้าตรวจได้ในไม่กี่วินาทีให้ตรวจ ถ้าตรวจไม่ได้ให้บอกว่าเป็นสมมติฐาน

เวลาแก้บั๊ก ให้ทำให้เกิดซ้ำได้ก่อน แล้วไล่หาสาเหตุต้นทาง การแก้ที่อาการโดยไม่รู้สาเหตุมักทำให้บั๊กย้ายที่

### 3. หาทางเลือกมากกว่าหนึ่ง

สำหรับการตัดสินใจที่ย้อนยาก (โครงสร้างข้อมูล, contract ของ API, การแบ่ง layer, โครงนำทางของแอป) ให้คิดอย่างน้อย 2–3 ทาง รวมถึงทางที่ง่ายที่สุดและทาง "ไม่ต้องทำอะไรเพิ่ม" เทียบด้วยเกณฑ์ที่เกี่ยวกับงานนี้จริง เช่น ความง่าย ความเสี่ยง ผลกระทบของเดิม แรงที่ใช้ แล้วเลือกพร้อมเหตุผลหนึ่งถึงสองประโยค

เลือกทางที่ง่ายที่สุดที่ตอบโจทย์ปัจจุบันครบ ความซับซ้อนที่เผื่ออนาคตมีต้นทุนแน่นอน ส่วนประโยชน์ยังไม่แน่

### 4. คิดล่วงหน้าว่าจะพังตรงไหน

สมมติว่างานนี้ส่งไปแล้วพังในหนึ่งเดือน สาเหตุที่น่าจะเป็นที่สุดคืออะไร ไล่ตามรายการนี้เฉพาะข้อที่เกี่ยว:

- ข้อมูล: ว่าง, null, ยาวมาก, จำนวนมาก, ซ้ำ, รูปแบบผิด, ภาษาไทยและ emoji, เขตเวลาและรูปแบบวันที่
- ลำดับเหตุการณ์: ส่งซ้ำ, กดสองครั้ง, สองคนแก้พร้อมกัน, มาถึงผิดลำดับ, ค้างกลางทาง
- สิทธิ์: ยังไม่ล็อกอิน, สิทธิ์ไม่พอ, เข้าถึงข้อมูลของคนอื่นด้วยการเดา id
- ภายนอก: เน็ตหลุด, ระบบอื่นช้าหรือล่ม, ตอบกลับไม่ครบ, สำเร็จครึ่งเดียว
- ของเดิม: ใครเรียกใช้ส่วนนี้อยู่, ข้อมูลเก่ารูปแบบเดิม, ต้อง migrate หรือไม่

### 5. ลงมือเป็นก้าวเล็กที่ตรวจได้

แบ่งงานให้แต่ละก้าวมีวิธีรู้ว่าถูก (typecheck ผ่าน, test ผ่าน, เปิดหน้าจอแล้วเห็นผล) ตรวจทีละก้าว ปัญหาที่เจอหลังเขียนไปห้าร้อยบรรทัดหาสาเหตุยากกว่าเจอหลังห้าสิบบรรทัดมาก

### 6. ตรวจด้วยหลักฐาน

- รันจริง: typecheck, lint, test, หรือเปิดใช้งานจริง แล้วอ่านผลลัพธ์ทั้งหมด ไม่ใช่แค่บรรทัดสุดท้าย
- ไล่ตัวอย่างด้วยมือหนึ่งกรณีปกติและหนึ่งกรณีผิดพลาด ผ่านโค้ดหรือ flow ที่ออกแบบ
- อ่าน diff หรือแบบที่ทำเสร็จอีกรอบในฐานะผู้รีวิวที่ไม่เคยเห็นงานนี้

"อ่านแล้วน่าจะถูก" ไม่ใช่หลักฐาน ถ้ารันไม่ได้ให้บอกตรง ๆ ว่ายังไม่ได้รัน

### 7. วิจารณ์งานตัวเองก่อนส่ง

ถามสามข้อ แล้วแก้สิ่งที่แก้ได้ก่อนส่ง:

1. ผู้รีวิวที่เข้มที่สุดจะโจมตีตรงไหนก่อน
2. มีส่วนไหนที่ไม่ได้ตรวจ หรือตรวจไม่ได้
3. ทำเกินหรือขาดจากที่ขอหรือไม่

### 8. สื่อสารผล

ขึ้นต้นด้วยข้อสรุปหรือผลงาน ตามด้วยเหตุผลของการตัดสินใจสำคัญ แล้วจึงบอกสิ่งที่ยังไม่แน่ใจและสิ่งที่เจ้าของต้องตัดสิน แยกให้เห็นว่าอะไรตรวจแล้ว อะไรยังเป็นสมมติฐาน

## เมื่อไรควรหยุดถาม

เจ้าของต้องการให้ถามเมื่อไม่แน่ใจ มากกว่าให้เดาแล้วทำผิด ขั้นตอนแปลงคำขอและรูปแบบคำถามอยู่ใน [requirements.md](requirements.md) สรุปกฎ:

- ถามก่อนลงมือ เมื่อมีจุดที่ไม่เข้าใจหรือตีความได้หลายทาง และคำตอบเปลี่ยนสิ่งที่จะสร้าง
- ไม่ต้องถาม เมื่อหาคำตอบได้จากโปรเจ็กต์หรือคำสั่งที่มีอยู่ หรือเมื่อทุกการตีความให้ผลเหมือนกัน
- รายละเอียดปลีกย่อยที่แก้ทีหลังได้ง่าย ให้เลือกค่าที่สมเหตุสมผล ทำต่อ และระบุไว้ในหัวข้อสมมติฐาน
- รวมคำถามเป็นชุดเดียว ไม่เกิน 4 ข้อ แต่ละข้อมีตัวเลือกและบอกว่าแนะนำข้อไหน

## สัญญาณว่ากำลังคิดตื้น

- เขียนชื่อ API หรือ option โดยไม่ได้เปิดดูว่ามีจริง
- แก้แล้วผ่านโดยอธิบายไม่ได้ว่าทำไมเดิมถึงพัง
- มีทางเลือกเดียวในหัวตั้งแต่ต้นจนจบ
- ออกแบบแต่เส้นทางที่ทุกอย่างสำเร็จ
- บอกว่าเสร็จโดยไม่มีผลรันหรือการไล่ตัวอย่างรองรับ
- แก้ไฟล์ที่ไม่เกี่ยวกับงานเพราะ "เห็นแล้วอยากปรับ"

## แบบฟอร์มให้กรอก

งานขนาดกลางขึ้นไป ให้เขียนแบบฟอร์มเหล่านี้ออกมาจริง ๆ ก่อนลงมือ การเขียนออกมาบังคับให้คิดครบ และให้เจ้าของเห็นความเข้าใจผิดตั้งแต่ต้น ห้ามข้ามแบบสรุปโจทย์แม้คิดว่าเข้าใจแล้ว

### แบบสรุปโจทย์ (ขั้น 1)

```text
เป้าหมาย: <ใคร> ต้องการ <อะไร> เพื่อ <ผลที่ได้>
เสร็จเมื่อ:
  1. <เกณฑ์ที่ตรวจได้ด้วยการรันหรือการดู>
  2. ...
ในขอบเขต: ...
นอกขอบเขต: ...
ข้อเท็จจริง (เห็นจากโค้ด/คำสั่ง): ...
สมมติฐาน (ยังไม่ได้ตรวจ): ...
คำถามค้าง: ...
ขนาดงาน: เล็ก / กลาง / ใหญ่ เพราะ ...
```

เกณฑ์ "เสร็จเมื่อ" ที่ดีคือคนอื่นอ่านแล้วตรวจได้ว่าผ่านหรือไม่ "ระบบทำงานได้ดี" ตรวจไม่ได้ "กดบันทึกแล้วรายการใหม่ปรากฏในตารางโดยไม่ต้องรีเฟรช" ตรวจได้

### ตารางเทียบทางเลือก (ขั้น 3)

```text
การตัดสินใจ: <ต้องเลือกอะไร>
| เกณฑ์            | ทาง A: ... | ทาง B: ... | ทาง C: ไม่ทำเพิ่ม |
| ตอบโจทย์ครบไหม   |            |            |                   |
| ความซับซ้อน      |            |            |                   |
| กระทบของเดิม     |            |            |                   |
| ความเสี่ยงถ้าผิด  |            |            |                   |
เลือก: ... เพราะ ...
ข้อเสียที่ยอมรับ: ...
```

### ตารางคิดกรณีพัง (ขั้น 4)

```text
| สถานการณ์            | เกิดอะไรขึ้นตอนนี้ | ควรเกิดอะไร | จัดการอย่างไร |
| input ว่าง/ผิดรูปแบบ |                    |             |               |
| ส่งซ้ำ/กดสองครั้ง    |                    |             |               |
| สองคนทำพร้อมกัน      |                    |             |               |
| ไม่มีสิทธิ์           |                    |             |               |
| ระบบภายนอกล้ม        |                    |             |               |
| ข้อมูลเก่ารูปแบบเดิม  |                    |             |               |
```

ตัดแถวที่ไม่เกี่ยวออก และเพิ่มแถวเฉพาะของงานนั้น

### แบบวิจารณ์ตัวเอง (ขั้น 7)

```text
จุดอ่อนที่สุดของงานนี้: ...
สิ่งที่ตรวจแล้วและวิธีตรวจ: ...
สิ่งที่ยังไม่ได้ตรวจ: ...
ทำเกินจากที่ขอ: ไม่มี / ...
ทำขาดจากที่ขอ: ไม่มี / ...
ความมั่นใจ: สูง / กลาง / ต่ำ เพราะ ...
```

ถ้าเจอจุดอ่อนที่แก้ได้ ให้แก้ก่อนส่ง แล้วค่อยเขียนแบบนี้ใหม่

## ตัวอย่างการใช้ครบทุกขั้น

คำขอ: "เพิ่มปุ่มยกเลิกคำสั่งซื้อให้ลูกค้า"

**ขั้น 1** เป้าหมาย: ลูกค้าต้องการยกเลิกคำสั่งซื้อของตัวเองได้เองโดยไม่ต้องติดต่อร้าน เสร็จเมื่อ: (1) ปุ่มแสดงเฉพาะคำสั่งซื้อที่ยกเลิกได้ (2) กดแล้วสถานะเป็น CANCELLED (3) คำสั่งซื้อของคนอื่นยกเลิกไม่ได้ คำถามค้าง: ยกเลิกหลังชำระเงินแล้วได้หรือไม่ ต้องคืนเงินหรือไม่

**ขั้น 2** เปิดโค้ดดู พบว่ามี `ORDER_STATUS` สามค่า มี `order.service.ts` และยังไม่มีระบบคืนเงิน ข้อเท็จจริงนี้เปลี่ยนคำถามค้าง: ถ้าให้ยกเลิกหลังชำระต้องสร้างระบบคืนเงิน ซึ่งเกินขอบเขต

**ขั้น 3** ทาง A: ยกเลิกได้เฉพาะสถานะ PENDING ทาง B: ยกเลิกได้ทุกสถานะพร้อมคืนเงินอัตโนมัติ ทาง C: ส่งคำขอยกเลิกให้ร้านอนุมัติ เลือก A เพราะตอบโจทย์หลักได้ด้วยของที่มี B ต้องสร้างระบบคืนเงิน แจ้งเจ้าของว่า A ไม่ครอบคลุมคำสั่งซื้อที่ชำระแล้ว

**ขั้น 4** กดสองครั้ง → ครั้งที่สองต้องได้ผลเดิม ไม่ error ยกเลิกพร้อมกับที่ระบบชำระเงินตอบกลับ → ใช้ `UPDATE ... WHERE order_status = 'PENDING'` แล้วตรวจจำนวนแถว เดา id ของคนอื่น → ตรวจความเป็นเจ้าของ คืน "ไม่พบ"

**ขั้น 5** ลำดับ: กฎ `canCancelOrder` + test → repository `cancelIfPending` → service → handler → ปุ่มในหน้าจอ

**ขั้น 6** รัน typecheck และ test ผ่าน ไล่มือกรณี "ยกเลิกคำสั่งซื้อที่ PAID" ได้ผลเป็นปฏิเสธพร้อมข้อความ ตรงตามที่ออกแบบ

**ขั้น 7** จุดอ่อน: ยังไม่ได้ทดสอบกรณีพร้อมกันจริง มีแต่เหตุผลจากเงื่อนไข SQL ระบุไว้ในรายงาน

**ขั้น 8** รายงานขึ้นต้นด้วย "เพิ่มการยกเลิกสำหรับคำสั่งซื้อที่ยังไม่ชำระแล้ว" ตามด้วยเหตุผลที่ไม่รวมกรณีชำระแล้ว และคำถามเรื่องคืนเงิน

## กฎกันพลาดเมื่อไม่แน่ใจ

ใช้เมื่อลังเลว่าควรทำอย่างไร เลือกข้อแรกที่ตรงกับสถานการณ์:

1. ไม่รู้ว่าฟังก์ชัน ไฟล์ หรือ option มีอยู่จริงหรือไม่ → ค้นหาหรือเปิดดู ห้ามเขียนจากความจำ
2. ไม่รู้ว่าโปรเจ็กต์ทำเรื่องนี้อย่างไร → หาตัวอย่างที่มีอยู่ในโปรเจ็กต์แล้วทำตาม
3. กฎสองข้อขัดกัน → คำสั่งล่าสุดของเจ้าของ > AGENTS.md ของโปรเจ็กต์ > สกิลนี้ > ความเคยชินทั่วไป ถ้ายังขัดให้ถาม
4. งานต้องใช้สิ่งที่ไม่ได้รับอนุญาต (package ใหม่, deploy, แก้ข้อมูลจริง) → หยุดและถาม
5. ทำตามคำขอตรงตัวแล้วจะเกิดผลเสียชัดเจน → ทำส่วนที่ปลอดภัย แจ้งผลเสีย และเสนอทางเลือก
6. ตรวจผลไม่ได้ → ส่งงานพร้อมระบุชัดว่าส่วนไหนยังไม่ได้ตรวจและตรวจอย่างไรได้
7. ติดอยู่ที่เดิมหลังลองสองวิธี → หยุด สรุปสิ่งที่ลองและผลที่ได้ แล้วถามเจ้าของ
