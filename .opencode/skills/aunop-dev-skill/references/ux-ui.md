# ออกแบบหน้าจอ UX/UI

ใช้เมื่อต้องออกแบบหน้าจอใหม่ ปรับหน้าจอเดิม ทำ wireframe/mockup หรือเขียนโค้ด UI หลักคิดคือ หน้าจอมีไว้ให้ผู้ใช้ทำงานหนึ่งอย่างให้สำเร็จ ความสวยมาทีหลังความเข้าใจง่าย

ค่าเริ่มต้น โครงหน้าจอตามชนิด กฎของส่วนประกอบ ข้อความตัวอย่าง และตัวอย่างสเปกครบชุด อยู่ใน [ui-patterns.md](ui-patterns.md)

## ลำดับการทำงาน

1. **ผู้ใช้และงาน:** ใครใช้ ใช้บนอุปกรณ์อะไร ในสถานการณ์ไหน (นั่งโต๊ะ, ยืนถือมือถือมือเดียว, กลางแดด) ต้องการทำอะไรให้เสร็จ และทำบ่อยแค่ไหน คำตอบเหล่านี้กำหนดขนาดปุ่ม ความหนาแน่นข้อมูล และจำนวนขั้นตอน
2. **สีและแนวหน้าตา:** โปรเจ็กต์ใหม่ให้ถามเจ้าของเรื่องสีหลัก ฟอนต์ และแนวที่ต้องการก่อนออกแบบหน้าแรก เจ้าของกำหนดเป็นรายโปรเจ็กต์ ระหว่างรอคำตอบใช้ token กลางและระบุว่าเป็นค่าชั่วคราว
2. **สำรวจของเดิม:** ถ้าโปรเจ็กต์มี component library, design token, หรือหน้าจออื่นอยู่แล้ว ให้ใช้ต่อ หน้าจอใหม่ที่หน้าตาไม่เหมือนส่วนอื่นของแอปคือข้อบกพร่อง แม้จะสวยกว่า
3. **รายการหน้าจอและการนำทาง:** ลิสต์หน้าจอทั้งหมดที่ flow ต้องใช้ และเส้นทางระหว่างหน้า ถ้ายังไม่มี flow ให้ทำตาม [system-design.md](system-design.md) ก่อน หน้าจอที่ออกแบบโดยไม่มี flow มักขาดหน้าระหว่างทาง
4. **สเปกรายหน้าจอ** ตามแบบด้านล่าง
5. **Wireframe** โครงสร้างและลำดับความสำคัญ ยังไม่ใส่สีและรายละเอียด ให้เจ้าของดูก่อนถ้างานใหญ่ เพราะแก้โครงตอนนี้ถูกกว่าตอนทำเสร็จ
6. **Visual design / โค้ด** ตามหลักในหัวข้อถัดไป
7. **ตรวจ** ด้วย checklist ท้ายไฟล์ และเปิดดูของจริงที่ความกว้างมือถือและจอใหญ่ถ้าทำได้

## สเปกรายหน้าจอ

| หัวข้อ | สิ่งที่ต้องระบุ |
| --- | --- |
| จุดประสงค์ | ผู้ใช้มาหน้านี้เพื่อทำอะไร หนึ่งประโยค |
| ทางเข้า / ทางออก | มาจากหน้าไหน ไปต่อหน้าไหน กด back แล้วเกิดอะไร |
| การกระทำหลัก | หนึ่งอย่างต่อหน้าจอ ปุ่มเด่นที่สุด |
| การกระทำรอง | สิ่งที่ทำได้แต่ไม่ใช่เป้าหลัก |
| ข้อมูลที่แสดง | field อะไร มาจาก API/schema ไหน เรียงและจัดกลุ่มอย่างไร |
| ข้อมูลที่รับ | ช่องกรอก ชนิด กฎตรวจ ค่าเริ่มต้น |
| สถานะ | ดูหัวข้อ "สถานะของหน้าจอ" |
| สิทธิ์ | role ไหนเห็นหรือทำอะไรได้ต่างกัน |

## สถานะของหน้าจอ

ออกแบบทุกสถานะที่เกิดได้ ไม่ใช่เฉพาะตอนมีข้อมูลสวย ๆ ผู้ใช้เจอสถานะเหล่านี้บ่อยกว่าที่คิด และเป็นจุดที่แอปดูพังที่สุดถ้าไม่ได้ออกแบบ:

- **กำลังโหลด:** skeleton หรือ spinner และกันการกดซ้ำ
- **ว่าง:** ยังไม่มีข้อมูล บอกว่าทำไมว่างและให้ปุ่มเริ่มต้น
- **มีข้อมูล:** น้อย (1 รายการ) และมาก (ยาวเกินจอ, ข้อความยาวเกินช่อง)
- **ผิดพลาด:** บอกว่าเกิดอะไรด้วยภาษาคน บอกวิธีแก้ และมีปุ่มลองใหม่
- **สำเร็จ:** ยืนยันว่าเกิดผลแล้ว และบอกขั้นถัดไป
- **ไม่มีสิทธิ์ / ออฟไลน์ / session หมดอายุ:** เมื่อเกี่ยวข้อง
- **สถานะของส่วนประกอบ:** ปกติ, hover, focus, กดอยู่, disabled, กำลังทำงาน

## หลักออกแบบ

**ลำดับความสำคัญ**
- หนึ่งหน้าจอมีการกระทำหลักหนึ่งอย่าง ปุ่มหลักมีแบบเดียวและเด่นที่สุด ปุ่มที่เด่นเท่ากันสองปุ่มทำให้ผู้ใช้ต้องหยุดคิด
- สิ่งสำคัญที่สุดอยู่บนสุดและใหญ่สุด ใช้ขนาด น้ำหนักตัวอักษร และระยะห่าง สร้างลำดับก่อนใช้สี
- จัดกลุ่มสิ่งที่เกี่ยวกันให้อยู่ใกล้กัน ระยะห่างในกลุ่มน้อยกว่าระหว่างกลุ่ม

**ความสม่ำเสมอ**
- ใช้ scale เดียวสำหรับระยะห่าง (เช่น 4/8/12/16/24/32) ขนาดตัวอักษร และมุมโค้ง เก็บเป็น token ไม่ใส่ค่าลอย ๆ ตาม [coding-standards.md](coding-standards.md) ข้อ 7
- สิ่งที่ทำงานเหมือนกันหน้าตาเหมือนกัน สิ่งที่หน้าตาเหมือนกันทำงานเหมือนกัน
- สีมีความหมายคงที่: สีหลักหนึ่งสีสำหรับการกระทำ, แดงสำหรับอันตราย/ผิดพลาด, เขียวสำหรับสำเร็จ และไม่ใช้สีอย่างเดียวสื่อความหมาย ให้มีไอคอนหรือข้อความกำกับ

**ฟอร์ม**
- label อยู่เหนือช่องและมองเห็นตลอด placeholder ไม่ใช้แทน label เพราะหายเมื่อเริ่มพิมพ์
- ขอเฉพาะข้อมูลที่จำเป็น ช่องที่ไม่บังคับระบุว่า "ไม่บังคับ"
- ข้อผิดพลาดแสดงใต้ช่องที่ผิด บอกวิธีแก้ ("รหัสผ่านต้องมีอย่างน้อย 8 ตัว" ไม่ใช่ "ข้อมูลไม่ถูกต้อง") และไม่ล้างข้อมูลที่กรอกไว้
- ใช้ชนิด input ให้ตรง (email, tel, number, date) เพื่อให้มือถือขึ้นคีย์บอร์ดถูก
- กฎตรวจฝั่งหน้าจอมาจาก schema เดียวกับฝั่ง server

**การตอบสนอง**
- ทุกการกดมีผลตอบกลับทันที งานที่นานกว่าหนึ่งวินาทีแสดงสถานะกำลังทำงาน
- การกระทำที่ย้อนไม่ได้ (ลบ, ส่ง, จ่ายเงิน) ต้องยืนยันโดยระบุชื่อสิ่งที่จะโดนกระทบ ถ้าทำ undo ได้ให้ใช้ undo แทนการถามยืนยัน
- ข้อความบนปุ่มเป็นกริยาที่บอกผล ("บันทึกการแก้ไข", "ลบรายการ") ไม่ใช่ "ตกลง"

**Responsive และการเข้าถึง**
- ออกแบบจากจอเล็กก่อน แล้วขยาย ระบุ breakpoint ที่ layout เปลี่ยน
- เป้ากดบนจอสัมผัสอย่างน้อย 44×44 px และห่างกันพอไม่ให้กดพลาด
- contrast ของข้อความกับพื้นหลังอย่างน้อย 4.5:1 (ข้อความใหญ่ 3:1)
- ใช้คีย์บอร์ดได้ครบ เห็น focus ชัด ใช้ element ตามความหมาย (`button`, `label`, heading เรียงระดับ) และรูปที่มีความหมายมี alt

**ภาษาไทย**
- เลือกฟอนต์ที่รองรับไทยจริง และตั้ง line-height ราว 1.5–1.7 เพราะสระบนล่างและวรรณยุกต์ต้องการพื้นที่ มิฉะนั้นจะถูกตัดหรือชนบรรทัดอื่น
- ไม่ใช้ letter-spacing กว้างและไม่ใช้ตัวพิมพ์ใหญ่ล้วนเป็นวิธีเน้นกับข้อความไทย
- ภาษาไทยไม่มีช่องว่างระหว่างคำ ตรวจการตัดบรรทัดและการตัดข้อความยาว (ellipsis) ด้วยข้อความไทยจริง
- วันที่แสดงเป็นตัวเลข วัน/เดือน/ปี ภาษาไทยใช้ปี พ.ศ. (`13/11/2569`) ภาษาอังกฤษใช้ปี ค.ศ. (`13/11/2026`) ตาม [owner-profile.md](owner-profile.md) รูปแบบตัวเลขและสกุลเงินใช้แบบเดียวทั้งแอป
- แอปเป็นสองภาษา ไทยและอังกฤษ: ข้อความทุกชิ้นมาจากไฟล์คำแปล และต้องตรวจหน้าจอทั้งสองภาษา ตามกฎใน [owner-profile.md](owner-profile.md)

## รูปแบบที่ส่งมอบ

เลือกตามสิ่งที่เจ้าของจะทำต่อ:

- **ยังคุยโครงสร้าง:** รายการหน้าจอ + สเปกรายหน้า + wireframe แบบกล่องข้อความ
- **อยากเห็นหน้าตา:** mockup ที่ดูได้จริง ถ้า session มีเครื่องมือออกแบบ (เช่น Figma หรือ artifact ชนิด Design) ให้ใช้เครื่องมือนั้น ไม่เช่นนั้นทำ HTML ไฟล์เดียวที่เปิดดูได้
- **จะใช้จริง:** โค้ด component ตาม stack และ convention ของโปรเจ็กต์ ตาม [coding-standards.md](coding-standards.md)

Wireframe แบบข้อความใช้เมื่ออยากให้เห็นโครงเร็ว:

```text
┌──────────────────────────────┐
│ ← รายการตรวจ            [+]  │  แถบบน: ย้อนกลับ, ชื่อหน้า, เพิ่มรายการ
├──────────────────────────────┤
│ [ค้นหา...................]   │
│ (ทั้งหมด) (รอตรวจ) (เสร็จ)   │  ตัวกรองสถานะ
├──────────────────────────────┤
│ จุดตรวจ A-01        ● รอตรวจ │
│ อาคาร 1 ชั้น 2      08:30    │  แตะแถว → หน้ารายละเอียด
├──────────────────────────────┤
│ ...                          │
└──────────────────────────────┘
ว่าง: "ยังไม่มีรายการตรวจ" + ปุ่ม "เพิ่มจุดตรวจ"
ผิดพลาด: "โหลดรายการไม่สำเร็จ" + ปุ่ม "ลองใหม่"
```

ทุกครั้งที่ส่งงานออกแบบ ให้บอกการตัดสินใจหลัก 2–4 ข้อพร้อมเหตุผล และสิ่งที่ยังเป็นสมมติฐาน เพื่อให้เจ้าของแย้งได้ตรงจุด

## หลีกเลี่ยงหน้าตาสำเร็จรูป

ก่อนลงสี เลือกทิศทางให้ชัดหนึ่งประโยค (เช่น "เครื่องมือทำงาน ข้อมูลแน่น อ่านเร็ว" หรือ "แอปผู้ใช้ทั่วไป โปร่ง เป็นมิตร") แล้วให้ทุกการเลือกสี ฟอนต์ และระยะห่างรับใช้ทิศทางนั้น หน้าจอที่ใช้ gradient ม่วง การ์ดมุมโค้งเงาฟุ้ง และ emoji แทนไอคอนโดยไม่มีเหตุผล จะดูเหมือน template ทั่วไปและไม่ช่วยงานของผู้ใช้

## Checklist หน้าจอ

- [ ] รัน `node <skill>/scripts/check-ui.mjs <ไฟล์.html>` แล้วไม่มี `[error]` และตรวจคู่สีใหม่ด้วย `--contrast`
- [ ] บอกได้ในหนึ่งประโยคว่าหน้านี้ให้ผู้ใช้ทำอะไร และปุ่มหลักมีปุ่มเดียว
- [ ] ครบทุกสถานะที่เกี่ยวข้อง: โหลด, ว่าง, ข้อมูลน้อย/มาก, ผิดพลาด, สำเร็จ
- [ ] ทุกหน้าจอมีทางเข้าและทางออก ตรงกับ flow
- [ ] ใช้ component และ token เดิมของโปรเจ็กต์ ไม่มีค่าสีหรือระยะลอย ๆ
- [ ] ฟอร์มมี label, ข้อความผิดพลาดบอกวิธีแก้, ไม่ล้างข้อมูลเมื่อผิด
- [ ] การกระทำที่ย้อนไม่ได้มีการยืนยันหรือ undo
- [ ] ใช้ได้ที่ความกว้างมือถือ เป้ากดใหญ่พอ contrast ผ่าน ใช้คีย์บอร์ดได้
- [ ] ทดสอบด้วยข้อความไทยจริง รวมข้อความยาว
- [ ] ข้อมูลทุกช่องจับคู่กับ field ใน schema/API ได้
